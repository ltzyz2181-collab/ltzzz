## 2. wallet-ops 隔离负测（A-2）

新增 `scripts/tests/wallet-ops-drill.test.mjs`：在临时目录里跑**真实 CLI**
（不改生产工作流、不写仓库），断言退出码与回执内容。

| 场景 | 结果 |
|---|---|
| 8 步全 success | exit 0，回执 ok=true |
| 任一步 failure | exit 1，failed_steps 指名 |
| 任一步 cancelled（超时/取消） | exit 1 |
| 缺 outcome 变量 | 记为 not_run 并 exit 1 |
| 全空环境 | 8 步全红，exit 1 |

**回执缺失的 fail-closed 门没有落地，已回退。** 该门需要改 `.github/workflows/ltzzz-wallet-ops.yml`，
而这份文件在 `knowledge/results/patchgate/post271/artifact-manifest.json` 的
`small_payment_release` 集合里逐字节锁定。改动后 `Small payment policy` run 44225933765
直接报 `manifest_source_bytes_changed:.github/workflows/ltzzz-wallet-ops.yml`——这正是红线该有的行为。
我没有选择重钉 manifest（那等于绕过发布件复审），而是把文件恢复到原字节，并把这道门登记为待复审提案。
残余风险很小：回执记录步骤自身失败时 run 已经是红的，"写了但文件消失"才会漏，属理论缺口。

## 3. `call-deepseek` 调用点审计（C-1）

判断是否显式写了 `thinking`（只读，不执行被扫描代码）。

审计前 8 处调用中 4 处继承默认值（`thinking='enabled'`, `maxTokens=8192`）。已全部补显式：

| 文件 | 处理 |

**没有改 `call-deepseek.mjs` 的默认值**——那会影响未审计的调用方，属于需要单独裁决的改动。

## 4. 卡契约检查（F1 的可执行化）

新增 `scripts/check-card-contract.mjs`：同一张卡同时出现 planner JSON 契约与 worker ROUTE 契约时，
标记 `split_required`。当前 `ops/deep-superagent/tasks` 下 84 张卡有 **6 张混写**
（含 DAILY-1 与 DAILY-2）。混写不等于必然失败（单席位卡实测仍能过），但它让
"模型可能答错半场"成为结构性风险，新卡应拆成两张。

该检查**没有**设为 CI 强制门：历史卡会因此变红。建议只对新建卡执行 `--strict`。
