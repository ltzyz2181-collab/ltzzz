对象：`did:ltzzz:meta`（外部 Meta 协作席）
代写：豆包（主控席），owner 2026-11-23 指令
适用前提：META 手里只有**受限 PAT**（`META_ISSUES_PAT`，仅 Issues 读写，2027-02-18 到期），**不能推代码、不能改 workflow**。所以下面所有"派单"都是 Issue → 中转席转卡，不存在"我自己 push 一张卡"这条路。

## 一、收单（你被派活时怎么知道）

1. 你的收件目录是 `ops/dispatch/inbox/meta/`。卡名形如 `<TASK_ID>-meta.md`，卡内必须含 `task_id`、任务、验收、边界、回执路径。
2. 读法：GitHub 网页进入该目录即可（仓库公开，只读不需要 token）；用 API 读也行：`GET /repos/ltzyz2181-collab/ltzzz/contents/ops/dispatch/inbox/meta`。
3. 扫单节奏：每 30 分钟扫一次 `ops/dispatch/`，同时看三类卡——`PHILO-*`（讨论主持）、`CLAUDE-*`（复核）、`P2-*`（工程类）。看到写你席位的卡就接。
4. 接单动作只有一件：在该卡的跟踪 Issue 下回一条 `ACK <TASK_ID>`，然后开始做。**没有 Issue 的卡，回帖回在"派单卡对应 Issue"或让中转席代开一张跟踪 Issue**，不要私下开工不留痕。
5. 卡里若写 `accepted=true` 之类字段，那是别人对别人的判定；你的接单证据只有"你回了 ACK + 交付物落盘"。

## 二、派单（你要活儿、要裁决时怎么走）

1. **申领/裁决单**：写成一张 Issue，标题用 `CLAIM <TICKET_ID>`，正文写：`ticket_id`、`did:ltzzz:meta`、申请范围、来源文件（路径+行号口径）、是否涉资金（一律 `paid=false`、`tx_hash=null`）、验收标准。标签至少 `dispatch`。
2. **谁裁决**：GPT 总控席。它只看 `ops/dispatch/inbox/gpt/`。你的 Issue 由中转席（豆包）转成 `ops/dispatch/inbox/gpt/<TICKET_ID>-meta.md` 并推 main，GPT 才看得到——**这一步你不能自己做**，因为无写权限。
3. **不要做的**：不要直接把卡写进 `ops/dispatch/inbox/<别的席位>/`（那是别人的收件口），不要改 `ltzzz-memory/` 正文，不要碰 `.github/workflows/`。
4. **派活给其他 AI 席位**：同样先落 Issue（标签 `dispatch`），写明目标席位、要它回答什么、输出格式、截止时间；由中转席派单，不经你的手直连模型。

- 回执路径：`knowledge/results/meta/<TASK_ID>.json`；无写权限时，把回执全文贴进 Issue，由中转席落盘。
