## 发现与独立复现

| 级别 | 原问题与复现结果 | 修复及边界 |
|---|---|---|
| P1 | `tallyVotes`只将1通过/1反对判为资金分歧；2通过/1反对得到`ok=true`且熔断为false，与提案的2:1资金分歧规则相反 | 混合通过/反对拒收并生成熔断信号；要求三个不同提供商的票，重复票、错提案绑定、缺时间不通过 |
| P1 | `verifyEvidence`记录`run_id_ok=false`却仍返回ok；可用`exists:true`索引冒充证据；允许绝对路径及仓库外文件 | 实读批准回执目录中的文件并计算哈希，校验实际运行号；禁止路径穿越、绝对路径及symlink越界，不再信索引的“存在”声明 |
| P1 | 试点累计10、每日采购20、对外30的常量原来没有参与计算；金额只做宽松Number转换，嵌套自由字段仍可进入结构 | 金额严格类型和微美元精度；累计、日额、步长和绝对示例上限均有反例。计算需要显式spendState；它仍是调用者提供的影子状态，没有原子资金预留，不是实际授权 |
| P1 | `--dry-run`仍向真实`POST /api/bounties`发带Key的请求，且不论响应都写`live_order=false`；模拟响应即使返回published和Key回显也会照存 | 本阶段彻底不发送POST、不读取Key；`--dry-run`明确变为**本地payload预览**。不冒充平台预演、不建单、不预留、不付款 |
| P2 | 平台原始搜索响应整份落盘，包含不需要的个人资料或反射值；HTTP/JSON失败也可能总报ok | 只保留统计、去重公开ID及城市范围；不保存原始档案/联系方式/响应正文。错误和无关JSON形状记partial_failure |
| P2 | 票据provider字段全由输入JSON自报，没有真正独立模型执行证明；ctx可称live | 票绑定提案ID与哈希，但仍明确`provider_execution_verified=false`；强制shadow、`spending_authorized=false`，拒绝live模式，未实现真票鉴别或利益冲突核验 |
| P2 | 千问Schema v2虽正常结束，仍放过缺follow_up_receipt、paid=null等条件 | 用真正Draft7Validator跑16组正反例；原稿有7组与任务要求不符。原输出与哈希保留，另存修正候选；不把候选偷偷替换进生产 |

原来的7项Node测试全通过，但上述反例仍能复现；“7/7通过”不足以证明设计规则已落实。复现只使用临时目录、假资料和mock网络，未向平台发POST，未读取真实凭证，没有真实Key泄露或真人订单发生的证据。
