## 3. 测量口径

- 卡：`ops/deep-superagent/tasks/DEEP-SUPERAGENT-20261117-DAILY-1.json`，`public_distributable`，25 个 ref（GROUP A 11 + GROUP B 6 + GROUP C 8）。
- 合格判据：每个 ref **恰好一条**合法 `ROUTE | <ref> | <route> | <reason>`；0 missing / 0 duplicate / 0 invalid / 0 多余行；加 `--require-all-five` 时还要求五类 route 都出现。
- `card` 模式 = 原卡原样；`worker` 模式 = 原卡 + 显式覆盖「你是 worker，不是 planner，不要回 planner JSON」。
- 每模型每次只发一次请求，失败只记录、不重试。

| # | 模式 | thinking | max_tokens | pro | flash | 回执 |
|---|---|---|---|---|---|---|
| 1 | card | disabled | 2048 | 0/19（返回 planner JSON，21 行非 ROUTE） | 0/19（同上） | `shadow-20261118T022602Z.json` |
| 2 | worker | disabled | 2048 | 8/19 | 19/19 覆盖，但 9 行被判 unknown_ref | `shadow-20261118T022700Z.json` |
| 3 | worker | disabled | 2048 | 8/25（只答 C 组） | **25/25，pass=true** | `shadow-20261118T022740Z.json` |

## 5. 四个发现

**F1 卡本身混了两套契约。** 同一张卡里既有「Planner deepseek: return ONLY JSON」，又有「Worker: return ONLY one line per ref」。两模型都选择了先满足 planner 契约，于是 ROUTE 行 0 条。这与「协调席没吐出路由行」是同一个失败面：不是模型不会分诊，是**指令在互相抵消**。生产上 planner 与 worker 应拆成两次调用或两张卡，而不是靠模型自己挑。

**F2 在 worker 口径下，Flash 没有更差，反而更全。** 同一提示词，Flash 25/25 全覆盖、无多余行、无 markdown；Pro 只覆盖 8/25（并停在 C 组）。此前「Flash 一次给齐多组路由行大概率更差」的猜测，在这张卡上不成立。

**F3 thinking 开启会把完成预算烧光。** `thinking=enabled` 时，4096 与 8192 两种预算下两模型都是 `finish_reason=length`、输出 **0 字符**。而 `scripts/call-deepseek.mjs` 的默认正是 `thinking='enabled'`、`maxTokens=8192`。任何沿用默认值调用长卡的既有入口，都有拿到空正文的风险。路由这类「短结构化输出」步骤应显式 pin `thinking=disabled`。

**F4 单样本。** 以上只测了一张卡、每模型各一次。Pro 的 8/25 也可能来自「WORKER COVERAGE 里写了三个席位」导致的自限，需要在拆卡后复测才能定性。
