## 修复

- GET 与 POST 都验证当前 MP 明文推送 Token 签名；未配置、错误签名和未经证实的直接云函数事件一律不能读写订单。当前 HTTP 路由不等于已验真的微信原生回调通道。
- 发货须逐项匹配本地订单的用户、渠道、商品、单件数量、原价、实付金额、环境及平台单号。字段缺失或不同保留待核，原始订单环境不被通知覆盖。本轮仅支持现有单件、无优惠的商品。
- 以数据库条件更新保证仅 pending 可以置 paid。已退款、已关闭、退款核对中的订单不能被迟到/并发发货改回 paid；重复平台单号只确认一次。
- XML 根节点正确解包，JSON/XML 分别返回对应格式；畸形、重复字段、DTD、过大与未配置的加密消息拒绝处理。
- 退款成功信号须匹配既有支付单、用户、环境、金额和退款单号；只置 `refund_pending_verification` 并暂停交付。当前没有经核验的退款申请台账及查询适配，不能将信号冒充最终退款成功。
- 下单必须有平台 OPENID，且与 code2Session 一致；清理原始 session、网络错误和上游错误回显。官方 code2Session 的 HTTPS GET 查询参数契约保留，不能仅因参数包含 secret 就认定已泄露。

## 接续部署

1. 登记豆包宿主先阻断旧回调的公网写入并报告实际控制台状态。邮件已发不代表阻断已发生。
2. 对此 PR 固定 head 做独立代码复核和 CI。实际审查提供商/模型按执行器回执填写，不能因席位名推定；未取得只记 pending。
3. 由持有既有 CloudBase 会话的豆包部署 `vpay-notify`、`vpay-order`；核实打包的源码 SHA256、环境、函数版本、UTC。不得用旧 main 包覆盖现有体验版，不为验收更改 `VPAY_ENV=1`、生产凭据、AppID 或添加上传白名单。
4. 先回读无签名/错签名请求拒绝且订单不变，再用官方实际沙箱事件核对字段和正确签名。合成签名 fixture 通过不等于平台真实支付回调成功。没有实际事件就保留 `pending` / `unverified`。
5. 覆盖取消、失败、未知、重复、跨用户、商品/金额/环境不符，以及退款后重放和并发状态；保留脱敏实际订单/任务 ID、代码哈希和接收结果，不保存 OPENID、请求签名、Token 或 session_key。
6. 前端 `refund_pending_verification` 文案随 1.0.2 候选交付。源码合并、云函数部署、体验版上传、备案通过、正式发布与真实收款分别记账。

止损/恢复优先级：无法证实新回调已部署时，继续阻断旧写入口；不能为“回滚”恢复无验签的旧回调。候选无官方事件可验时，不宣布真实收款链路已通。主动 xpay 查询与完整退款台账为后续切片，不能用现有普通微信支付 `/v3` 查询代替。

## 协议依据及未覆盖范围

已读取腾讯官方仓库 [CloudBase 虚拟支付参考](https://github.com/TencentCloudBase/skills/blob/main/skills/cloudbase-wechat-integration/references/virtual-payment.md)，区分明文入站 Token 签名、出站 paySig 和退款成功条件。该参考指向的微信独立文档在当前工具不可读取，实际平台 payload/配置仍须部署宿主核验。

当前按已报告的明文 JSON 推送部署，未迁移 AES 安全模式。明文 Token 签名不绑定 body，依赖 HTTPS 及签名参数保密；不要记录或公开合法通知的签名 URL。安全模式应另取官方配置与测试向量，不能自行切换模式冒充兼容完成。没有新增主动查单定时、付费 cron、资金请求或模型调用。
