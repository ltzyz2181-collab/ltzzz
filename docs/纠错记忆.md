## C-20261117-01 凭据明明已有，却向 owner 索取（重复劳动）

- 时间：2026-11-17
- 场景：服务号开放标签（B 路线）签名部署
- 我做的错事：直接向 owner 要「服务号 AppID / AppSecret」，并说"给我这两项就能做完"。实际上东西早在仓库与已部署服务里，我自己查得到。
- 错在哪一步：
  1. **没先查仓库**。`wrangler.wechat.toml:9` 写着 `WECHAT_EXPECTED_APP_ID = "wxdabcfdf41f413f33"  # owner确认的服务号`；`docs/wechat-account-mismatch-2026-10-11.md` 记录 owner 确认后台尾号 `413f33`；`ops/密钥台账-v2.md` 记录公众号凭据"已具备"。
  2. **没先查已部署服务**。Cloudflare worker `ltzzz-wechat-publisher` 的 `/health` 返回 `{"app_id":true,"expected_account_matches":true,"has_secret":true,"has_token":true}` —— AppID 与该 AppSecret 早已配好且可用。
  3. **把"仓库没有明文 Secret"错当成"没有凭据"**。正确区分：明文不入库是安全规范，不等于凭据不存在；凭据在加密存储（CF Worker Secret / GitHub Secrets），使用时不需要读明文。
  4. **结论也写错了**。把"B 路线唯一硬阻塞是凭据"写进已闭环清单 §3，等于让 owner 再交一次他已经给过的东西。
- 正确做法（以后照此）：
  - 判定"缺凭据"前，固定按顺序查四处：① `wrangler*.toml` 的 `[vars]` / `*_EXPECTED_*`；② `ops/密钥台账*.md`、`docs/*CREDENTIALS*`；③ `docs/wechat-account-mismatch-*.md` 一类勘误档；④ 已部署服务的 `/health`（`has_secret`、`expected_account_matches` 本身就是就绪证据）。
  - 要用凭据签名时，优先**复用已持有凭据的运行体**（在 worker 内新增签名路由），不要把明文搬到新环境、也不要把明文发到对话里。
  - 索要凭据只有在上述四处都查过且都无果时才允许，且必须同时贴出"查了哪四处、各自返回什么"。
- 触发条件：任何"需要 AppID / AppSecret / API Key / Token / 密钥"的判断。
- 校验方法：开口要凭据之前，必须能贴出四处的检索结果（文件路径+行号，或 health 的 JSON 字段）。
- 已做的更正：`docs/2026-11-16-已闭环事项登记与勿重复清单.md` §3 已改写为"凭据已有；真正缺口是服务号后台配置（关联小程序 / JS 接口安全域名）"。

## C-20261117-02 拿会变的出口 IP 去填固定白名单（方案本身错了）

- 时间：2026-11-17
- 场景：服务号 JS-SDK 签名（B 路线），worker `/jsapi-sign` 报 40164
- 我做的错事：看到 40164 里的 `whitelist_ips:["104.23.251.139","104.23.251.45"]`，就把这两个 IP 当成"worker 的出口 IP"往微信 IP 白名单里填。
- 错在哪一步：
  1. **把一次观测当成常量**。同一天再请求一次，出口变成 `104.23.166.6/.7`，填进去的立刻作废。
  2. **没先判断"这个运行体有没有固定出口"**。Cloudflare Workers 的 egress 是共享池，天然不固定；微信白名单只收单 IP、不收网段，所以这条路在架构上就不成立。
  3. **把"人工扫码"当成可以自动化掉的步骤**。微信对 IP 白名单修改强制管理员扫码，这不是技术障碍，是平台安全设计，绕不过去也不该绕。
- 正确做法（以后照此）：
  - 动白名单前先问一句：「这个调用方的出口 IP 稳定吗？」用两次不同时间的请求比对（40164 诊断里带着出口 IP，可直接当探针）。
  - 出口不稳定的运行体（CF Workers / Serverless / 动态 NAT）**不要**进 IP 白名单方案；改用固定 IP 的主机（本项目：云主机 `101.201.47.30`），或走微信官方「云托管免鉴权」通道。
  - 需要扫码时，明确告诉 owner「这是一次性人工门」，扫完写进本文件，下次不再要求。
- 触发条件：任何"给第三方平台加 IP 白名单 / 固定出口 IP / 配置可信来源"的任务。
- 校验方法：填白名单前后各做一次真实调用，比对诊断里报的出口 IP 是否与填入值一致；不一致就说明方案选错，立刻停手换架构，不要连续重试。
- 关联更正：`docs/2026-11-16-已闭环事项登记与勿重复清单.md` §3.1 已记录 CF 出口轮换实测与云主机固定出口方案。

## C-20261117-03 微信后台「点了没反应」不是页面坏了，是坐标偏了

- 时间：2026-11-17
- 场景：服务号后台 功能设置 / 基本配置 页
- 我做的错事：连续 6+ 次点「设置」「查看」都无响应，误判为"链接失效/接口 404"，浪费多轮。
- 错在哪一步：只调了一次坐标就反复重试，没有意识到 `cu` 坐标要按截图渲染尺寸换算（整屏 1763×1175，截图 1590×1067），且文档内按钮命中点还要再**上移约 11–12 渲染 px**。
- 正确做法：
  - 坐标换算：`x = 渲染px ÷ 1590 × 1000`，`y = 渲染px ÷ 1067 × 1000`；点了没反应时先按 -11/-12 渲染 px 微调 y 再试一次。
  - 仍无响应就直接上 F12 控制台：`[...document.querySelectorAll('a')].filter(a=>a.textContent.trim()==='查看').forEach(a=>a.click())` —— 微信后台这些弹窗都是 JS 唤起，控制台点一定生效。
  - 对话框里的多行 textarea，`cu.type` 里的 `\n` 会被吞，必须 `hotkey("enter")` 逐行敲。
- 触发条件：`mp.weixin.qq.com` 后台任何弹窗类操作（设置/查看/修改/保存）。
- 校验方法：点到即截图确认弹窗标题（如「查看IP白名单」「IP白名单设置」）出现，再往下走；没出现就是没点中，别再重复同一次点击。

## C-20261117-04 判断"出口 IP 是否固定"必须用目标服务+同一条网络路径，不能用通用 IP 回显

- 时间：2026-11-17 深夜
- 场景：给云主机签名服务定 IP 白名单
- 我做的错事：拿 `curl -4 https://ifconfig.co` 得到的 `101.201.47.30` 就去后台填白名单，还在邮件里写成"云主机固定出口"。后来用真服务打微信接口才发现：node 出的请求微信报的是 `101.126.47.141`、`101.126.82.227`，两个完全不同的 IP。
- 错在哪一步：
  1. **把"某一进程的出口"当成"主机的出口"**。本机直连出口是轮换池（`115.190.x` / `180.184.x` / `101.126.x` / `60.205.x` 都出现过）；`101.201.47.30` 是平台出网代理（`https_proxy`）的出口，只对"读代理环境变量的客户端"成立。
  2. **用 curl 的结果代表 node 的结果**。`curl` 默认读 `https_proxy` → 走代理 → 固定；node 的 `fetch`/`node:https` 默认**不读**代理 → 走直连 → 轮换。同一台机器，两个进程，两个出口。
  3. **没有在"真实调用路径"上验证**。应该直接用要上线的那段代码去打要打的那个第三方接口，看对方报回来的 IP。
- 正确做法（以后照此）：
  - 判出口固定性，**必须用目标服务当探针**：微信 40164 的 `errmsg` 里直接带 `invalid ip <IP>`，这就是免费的出口 IP 回显，比任何第三方 IP 查询都准。
  - 必须用**同一进程、同一客户端库、同一环境变量**去测，不要用 curl 测 node、不要用代理路径测直连路径。
  - 出口判定三件套一起记：`curl（走代理）` / `同语言客户端原样` / `curl --noproxy '*'`，三者不一致就说明存在双路径，白名单只能填"真实调用路径"那个。
  - 记录"这个 IP 依赖什么前提"：本例 `101.201.47.30` 依赖平台代理可用 + `HTTPS_PROXY` 保留，不是主机固有属性。
- 触发条件：任何"给第三方配置 IP 白名单 / 上报固定出口 / 判断某服务能不能进可信来源"的任务。
- 校验方法：服务起好后连续请求目标接口 ≥3 次，看诊断里报的 IP 是否每次都等于填进白名单的那个；只要有一次不等，立即停手，不要继续重试。

## C-20261117-05 "三次一致"不等于固定；假 appid 探针根本测不到白名单

- 时间：2026-11-17 晚（C-04 之后不到一天，同类错误复发）
- 场景：白名单扫码通过后，验证云主机签名服务是否真能调通微信
- 我做的错事（两处）：
  1. **把"同一分钟 3/3 一致"当成"出口固定"**，写进文档与邮件。当晚复测：`101.201.47.30` → `59.110.233.245` → 90 秒后 `123.56.59.76`。代理出口是**池**，不是固定地址。
  2. **手抄 18 位 AppID 去当探针**，连错两个字符（`wxdbabcfdf…`、`wxdbacfdf…`），微信回 `40013 invalid appid`。而 `40013` 在**IP 校验之前**返回，等于探针压根没走到白名单那一步，却被我当成"白名单没生效"继续排查。
- 错在哪一步：
  - 稳定性判定缺少**时间维度**：并发/短窗口一致 ≠ 长期一致，必须跨时段（≥90 分钟、至少两个时间点，最好跨小时）采样。
  - 探针缺少**变量隔离**：验证 IP 白名单必须固定"appid 正确、secret 故意错"这一个变量，appid 一错就测不到 IP。
  - 仍然**手抄长 ID**：仓库里就有一份权威值，应该 grep 取值，不是凭 OCR/记忆敲。
- 正确做法（以后照此）：
  - 探针模板（唯一允许的写法）：
    ```bash
    APPID=$(grep -oE 'wx[a-f0-9]{16}' wrangler.wechat.toml | head -1)
    curl -s "https://api.weixin.qq.com/cgi-bin/token?grant_type=client_credential&appid=${APPID}&secret=FAKE_PROBE_SECRET"
    ```
  - 错误码含义先背下来再排查：`40013`=appid 错（测不到 IP）；`40164`=IP 不在白名单（**errmsg 里就是出口 IP**）；`40001/40125`=IP 已过、secret 错。
  - 出口稳定性结论必须写清"采样时间点 + 采样次数 + 是否跨时段"，不允许只写"3/3 一致"。
  - 一旦确认出口会轮换，**立即停止往白名单塞 IP**，改判架构问题（换固定 EIP / 换免鉴权云托管 / 放弃该能力），不要"再试一次"。
- 触发条件：任何"固定 IP / 固定出口 / 白名单 / 可信来源"类判断；任何需要用第三方服务诊断码反推自身网络属性的场景。
- 校验方法：改完白名单后，用上面的探针在**两个相隔 ≥90 分钟的时间点**各测 3 次，`errmsg` 里报的 IP 必须与白名单一致；不一致就是架构性不可行，直接进裁决，不做第 4 次尝试。

### C-20261117-08 公开仓库里不给私人邮件留标题

- 现象：我把 Gmail 全箱 1366 封的「短标题」写进 `knowledge/results/deep-superagent/mail-fullbox/latest.json` 并推到 public main，里面有 Coinbase 登录验证码、Duolingo、SoFi 对账单等与项目无关的私人邮件标题。
- 根因：脚本只做了"金额/令牌脱敏"，把"脱敏"当成"可以公开"，没有做"项目相关性"过滤；而仓库是 public。
- 修法：`collect-gmail-imap.py` 增 `PROJECT_DOMAINS` 白名单（agent.qq.com / github.com / 微信系 / tencent / x.ai），非项目渠道邮件只计数 `project_unrelated_count`、标题不落盘；产物显式写 `subject_scope=project_domains_only`、`contains_mail_body=False`。
- 判定顺序：写任何"外部世界内容"进仓库前，先问三句——仓库是不是 public？这批数据里有多少是别人的？过滤条件写在生成脚本里了吗？
- 残留：旧 blob 仍在历史里；清历史需 owner 决定，不能自行 `filter-branch`。
