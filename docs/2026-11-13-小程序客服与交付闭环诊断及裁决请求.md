# 小程序客服与交付闭环诊断 + 裁决请求（2026-11-13）

触发：owner 于 2026-11-13 05:57 实付 ¥9.90 测试单后，在「世章 AI 助手」客服会话留言「为什么没有自动回复 收到信息回复」，无回应；随后问：AI 没有接入自动客服吗、文件发哪里、怎么才能完成订单、谁开发、谁做客服与跟进。

## 一、结论先行

1. **没有接入自动客服，代码层确认**。小程序只有原生客服按钮 `open-type="contact"`（`miniprogram/pages/orders/index.wxml:25`），点进去是微信「客服会话」。仓库里没有任何客服消息回调、关键词自动回复或转人工服务：云函数只有 `order-list / order-query / pay-create / vpay-order / vpay-notify` 五个，全部与支付、查询、退款有关。全仓库唯一与自动回复相关的是一份公众号版文案方案 `docs/wechat-reply-templates.md`，**没有对应实现代码**。
2. **微信后台是否配了欢迎语/自动回复：未核验**。这属于平台侧配置（小程序后台「客服」或微信客服工作台），不在仓库里；本轮未登录后台核对，按 unverified 处理。
3. **材料投递没有结构化入口**。用户只能把文件发进客服会话，我们没有接收端（无云存储写入、无邮箱入口、无工单号绑定），收件全靠人盯微信。
4. **交付状态没有写入者，订单会永远停在「已支付 · 待交付」**。`orders/index.js:10-17` 的展示层支持 `delivered`，但 `cloudfunctions` 里没有任何写 `delivered` 的代码（`vpay-notify` 只在 :100/:114/:139 做状态校验与退款）。没有管理端函数把订单改成已交付。
5. **当前这单的真实状态**：`out_trade_no VP20261112215711c7e626e9`，`product_id source_check`，`amount 990`，`created_at 2026-11-12T21:57:11Z`，`paid_at 2026-11-12T21:57:27Z`，`status paid` —— 即客户已真实付款，货未交付，SLA 24 小时按客户侧 2026-11-14 05:57 到期。集合 `orders` 共 15 条，除该单外其余历史单均为 `paid_at: null`。

## 二、逐问回答（按事实，不含推测）

**Q1 AI 有没有接入自动客服**
没有。且当前会话形态下，即使接入 API，客户发一句「你好」也只会进客服消息队列，需要服务端在 48 小时窗口内用客服消息接口主动回，仓库里没有这个服务端。

**Q2 文件发哪里**
现状唯一路径：微信客服会话（客户直接把文件/图片发给「世章 AI 助手」）。这条路径的问题是没有留档、没有订单绑定、客服离线就断。可选结构化入口三条（待裁）：
- A 邮箱收件：客户把材料发到指定邮箱，主题带订单号；优点零开发，缺点客户多一步、附件大小受邮箱限制。
- B 小程序内上传：新增云存储上传 + 订单号绑定，材料落库可追溯；优点体验最好、可审计，缺点要开发与容量/费用。
- C 客服会话 + 工单登记：保持现状，但要求客服收到即把订单号、材料清单登记到 `orders` 的一个 `intake` 字段；优点最快上线，缺点依赖人。

**Q3 怎么才能完成订单（现状 vs 需要的三步）**
现状链路缺两环：`pending → paid`（支付回调，已有）→ **材料接收（缺）** → 人工核对出报告 → **交付回写 delivered（缺）** → 订单页显示交付物。
所以这单目前不可能在系统里走完，只能人工线下交付、再由人手动改库。最小闭环需要：
1. 材料入口（上面 A/B/C 选一）；
2. 一个管理端云函数 `order-deliver`：只允许管理员 openid 调用，写 `status: delivered`、`delivered_at`、`deliverable_sha256`、`deliverable_note`；
3. 订单页展示交付结果与下载入口（现有 `delivered` 文案已在，补交付物区块）；
4. SLA 提醒：`paid` 超过 23 小时未 `delivered` 时告警，超过 24 小时按协议触发退款选项（是否自动触发需裁）。

**Q4 谁开发、谁做客服与跟进**
- 开发：Deep（代码 + CI + 云函数部署；按既定分工代码与 CI 归 Deep）。
- 客服首响与工单归集：AI 侧（豆包席位）可做模板化首响、把「订单号 + 材料清单 + 承诺 24 小时」登记进 `orders`，避免客户干等。
- 交付与退款终判：必须是人（owner），且沿用仓库既有规矩——订单与退款的终态判断只由 GPT 席位裁，豆包/WorkBuddy 只取证上报。
- 结论：AI 承担首响与登记，人承担交付与终判；不存在「AI 全自动客服+交付」这一档，除非补齐上面两环并接受自动退款风险。

## 三、方案比较（供裁）

| 方案 | 材料入口 | 首响 | 交付回写 | 开发量 | 风险 |
|---|---|---|---|---|---|
| 最小（1 天） | C 客服会话 + 工单登记字段 | 人工值守 + 后台自动回复文案（若后台支持） | 人工改库或补 `order-deliver` | 小 | 依赖人、易漏单 |

## 四、请裁决（A–E）

- A. 客服自动回复走哪条：① 零代码，微信后台配欢迎语与关键词（人工配，最快）；② 接客服消息 API 云函数（Deep 开发，需 access_token、IP 白名单与 48 小时窗口）；③ 先 ① 后 ②。
- B. 材料入口：A 邮箱 / B 小程序内上传 / C 客服会话 + `intake` 登记字段；是否两者并行。
- C. 是否批准新增 `order-deliver` 云函数（管理员 openid 白名单，写 delivered + sha256 + 时间），以及是否同时补订单页交付区块。
- D. 客服值守责任：AI 首响 + 人终判是否成立；SLA 24 小时超时是否**自动**触发退款，还是只告警、由人确认。本席建议只告警，退款仍人判。
- E. 对外文案是否统一写明「客服为人工响应，24 小时内处理；AI 不作自动承诺」，避免客户把无回复理解成故障（当前这单已发生）。
