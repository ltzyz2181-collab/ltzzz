# 反思机制：从错误中学习（Harness 反思层）

作者：Claude（独立规划/审计席，Sonnet 5.5）。性质：设计加可运行的参考实现，**默认不接入任何工作流**，不调用模型，不碰资金、密钥、信任根。由豆包合并并接线，GPT 总控按原任务编号登记，千问或另一家做原生复核。

## 一、owner 要的是什么

各 AI 重复掉进同一个坑。要的是一个闭环：**观到错误 → 写进知识库 → 下次做类似的事之前先看到它 → 真的改变做法 → 能量出有没有再犯。**

## 二、仓库里已有的，和缺的

| 已有 | 做什么 | 缺什么 |
|---|---|---|
| `data/reflections/*.md` 每日读后感 | 读核心记忆后的感想 | 不是由错误触发，也不会被下次任务取用 |
| `data/memory/<ai>.json` | 每个 AI 的上下文摘要 | 记的是做了什么，不是错在哪、规则是什么 |
| 工作池的 `preflight` 块 | 行动前写目标、未知项、停止条件 | 没有“已看过历史教训”这一项 |
| `scripts/check-core-memory.mjs` 等 | 个别坑的专用检查 | 每个坑单独写，没有统一台账，也看不出重犯 |

所以缺的不是又一篇反思文章，而是**一本能被检索、能被强制、能统计重犯的错误台账**。

## 三、先说实话：模型不会因此“变聪明”

模型的权重不会因为写了一条教训而改变。这里的“学习”只有三种真实的形式，按可靠程度排序：

1. **变成机器检查**（测试、CI 守卫）：违反就过不了，不依赖谁记不记得。最可靠。
2. **行动前强制取用**：`preflight` 必须逐条回应相关的强制教训，没回应就失败。依赖执行者认真对待，但至少留下可核对的痕迹。
3. **建议性提示**：只展示，不强制。最弱，但成本最低。

台账里的每条教训要向 1 靠拢：**同一个坑第二次出现，就说明写规则没用，必须升级成机器检查**，而不是把规则写得更长。

## 四、怎么运转

```
观（发现错误）→ 记（教训文件）→ 审（异供应方复核）→ 用（preflight 取用）→ 量（重犯统计）
```

1. **观**：来源可以是被拒的回执、失败的运行、审计发现、外部平台的拒收记录。`node scripts/lessons.mjs draft <回执.json> --agent <犯错的供应方> --reporter <记录者>` 生成骨架，并自动写入证据文件的 SHA256。骨架里的原因一律是“假设”，不会自称已证实。
2. **记**：一条教训一个文件 `knowledge/lessons/L-YYYYMMDD-NNN.json`（格式见 `protocol/lesson.schema.json`）。必填：实际犯错的供应方（不是席位名）、可观察的事实、证据路径和哈希、**一句**规则、对应的检查种类、签名 `signature`（同一个坑的固定名字，用来判重犯）。
3. **审**：升为 `adopted`（可强制）必须有**不同供应方**的接受评审；自己写自己的错不算数。要设为“强制”必须原因已验证、且证据被记录者核对过。升为 `verified` 必须有测试或 CI 守卫。
4. **用**：任务开工前运行 `retrieve --tags <任务标签>`；`preflight` 里增加 `lessons_considered: [{id, applied, note}]`。`check-preflight` 会拒绝：漏掉强制教训、引用不存在的编号、没写说明。建议性教训（`observed`）只展示，不挡路。
5. **量**：同一个 `error_class:signature` 再次出现时，`recurrence` 命令告诉你规则失效、必须升级成机器检查；`stats` 汇总每类错误的数量和“采纳后仍重犯”的次数。**这个数字才是“有没有学会”的证据。**

## 五、防止它自己出问题

- **只能更谨慎，不能放松**：教训的 `effect` 固定为 `adds_caution_only`，规则里出现“忽略、绕过、跳过检查、关闭检查”等字样会被拒绝。教训不能解锁资金、密钥、A2/A3、信任根，也不能改核心观。
- **防自圆其说**：错误的当事方不能给自己的教训盖章。
- **防事后合理化**：证据必须是文件路径加哈希，或链接；`verified_by_reporter` 如实标注是否亲自核对过。
- **防膨胀**：每条教训最多 8 个标签，一句规则；过期的标记 `retired`，不删除。
- **防中毒**：教训文件走分支加 PR，和代码一样由独立方审。工作流只读，不自动写入教训。

## 六、外部练手的数据怎么进来

每次外部平台任务的回执（接受、拒绝、超时、平台反馈）如果是失败类，就跑一次 `draft` 生成教训骨架：证据是平台记录本身，标签用任务类型（如 `external_task`、`code_review`），签名是具体的坑。成功的任务不生成教训，避免台账变成流水账。这也是 M1 里“完成以平台记录为准”的延伸：错误以平台记录为准。

## 七、桌面版 Harness 怎么用

台账是仓库里的普通文件，命令是 Node 22 零依赖。DeepSeek 桌面版只要能拉仓库、能跑 `node`，就可以在本机执行 `retrieve` 并把结果放进自己的上下文；不需要云端版。写回仍走分支加 PR。

## 八、本次提交包含什么

- `scripts/lib/lessons.mjs`、`scripts/lessons.mjs`：校验、检索、preflight 检查、重犯识别、统计、骨架生成。
- `scripts/tests/lessons.test.mjs`：11 项，覆盖不能放松、需异供应方评审、强制需已验证原因、重犯升级、加载器拒绝坏文件。
- `protocol/lesson.schema.json`。
- `knowledge/lessons/`：8 条种子，全部来自仓库里真实发生并有记录的错误，**状态都是 `observed`（只建议、不强制）**，等豆包或千问复核后再升级。其中 5 条证据是项目历史/重要事件的叙述，我只读了文字、没有复核原始回执（`verified_by_reporter:false`）。

## 九、豆包合并步骤（不改现有文件的最小接线）

1. 合并本 PR 后运行 `node --test scripts/tests/lessons.test.mjs` 与 `node scripts/lessons.mjs validate`。
2. 在 `scripts/lib/workpool-policy.mjs` 的 `validatePreflight` 末尾调用 `checkConsidered(record, lessons, tags)`；标签取自任务卡。先只记录告警，不挡 PR，跑一周后再改为必须通过。（该文件归 GPT 总控，改动请走 PR 并由千问复核。）
3. 工作流里增加一步 `node scripts/lessons.mjs validate`，只读。
4. 对种子逐条复核：用原始回执核对，通过则把状态改 `adopted` 并填 `review`（评审方必须不同于 `agent_actual.provider`）。
5. 两周后跑 `node scripts/lessons.mjs stats`，看“采纳后仍重犯”是否下降；没下降的类别升级成 CI 守卫。

## 十、未验证

没有接入真实工作流，也没有在真实的 DeepSeek 桌面环境里运行；本机测试通过只说明代码按设计工作，不说明各 AI 会因此少犯错。效果只能由第九节第 5 步的统计来证明。
