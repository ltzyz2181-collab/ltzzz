## 二、三条通道的区别（这是本轮最需要写清的部分）

仓库里现在并存三类「能跑大模型」的路径，性质完全不同，不能混为一谈：

| 维度 | ① 本地客户端 + DeepSeek 直连（本轮新增） | ② 第三方中转 APIsRouter（现有 relay seat） | ③ 逻辑席位 + 国内模型代表团（现有 gpt/claude 席） |
|---|---|---|---|
| 客户端 | OpenAI Codex / Anthropic Claude Code（原厂壳） | LTZZZ relay proxy → APIsRouter | GitHub Actions 里 call-*.mjs |
| 模型提供方 | DeepSeek 官方，**真原厂** | 第三方聚合，转卖 GPT/Claude 等 | deepseek-v4-pro / doubao-seed-2-1-pro / qwen-max |
| 凭证归属 | 自己持有的 DeepSeek key | 站点 key 只在服务端 Secret，席位只持 proxy token | 各厂 key 在 Actions Secrets |
| 数据路径 | 本机 → api.deepseek.com | 本机/Worker → 第三方站点 → 上游厂商，**日志留在第三方服务器** | 本机 → 各厂官方端点 |
| 证书性质 | 模型原厂、客户端原厂，可称「DeepSeek 官方」 | `official_provider_attestation=false`、`native_provider=false` | 同样必须记真实 provider，不能称原厂 |
| 使用限制 | 无网关配额，受 DeepSeek 账号额度限制 | 只允许长上下文/批处理（≥4096 token），余额 <3 USD 自动关席，短请求 400 | 受 Actions 额度与各厂 key 限制 |
| 我能操作 | 是（本机 CLI/GUI 都由我碰） | 否（我只读得到状态，调用在 Worker） | 否（在 Actions 里跑） |

一句话区分：
- **①是「原厂模型 + 原厂客户端，但没有原厂账号」**——模型是真的 DeepSeek，客户端是真的 Codex/Claude Code，只是背后不是 OpenAI/Anthropic 的模型
- **②是「原厂模型的转卖通道」**——模型可能是 GPT/Claude，但传输经过第三方，拿不到原厂证书，且有余额与长上下文闸门
- **③是「原厂名号 + 国产模型代跑」**——席位叫 GPT/Claude，实际执行的是 DeepSeek/豆包/千问，回执必须写 actual provider

风险差别：
- ①的风险是 **key 泄露**与**代码内容流向第三方厂商**，没有账号封禁风险（请求根本不发往 OpenAI/Anthropic）
- ②的风险是 **第三方留存日志**、**余额耗尽静默关席**、**被误读成原厂调用**
- ③的风险是 **名号与事实不符**，容易被下游当成原厂能力引用

## 四、我的建议（按「能让 GPT 直接裁」的方式写）

### 4.1 通道分层登记（建议采纳，不改任何权限）

给每条调用加一个必填字段 `provider_plane`，三选一：

- `native` = 原厂直连（目前只有 DeepSeek 官方满足）
- `relay` = 第三方中转（APIsRouter）
- `delegated` = 国内模型代跑原厂席位

好处：以后任何回执都能一眼看出「谁在跑、经谁跑、算不算原厂」，不用再靠人记。成本：改 receipt schema 一处，历史数据不动。

### 4.2 席位职能的四条调整建议

1. **GPT 只裁不写稿**：现在 GPT 席既要终审又要出方案，容易自己给自己背书。建议提案统一由执行席产出，GPT 只出裁决与理由——本提案就是照这个规矩写的。
2. **千问加一条「数字复算」**：现在千问是评审＋副协调，建议明确它必须对交付里的关键数字做一次独立复算（本轮 479/43.55/92 我算过，但这是我自证；有第二人复算才算证据）。
3. **DeepSeek 席限定在批量与结构化产出**：`deepseek-chat` 没有上下文元数据，长任务会提前截断，不适合当交互式主力。建议日课、批处理、结构化抽取归它，实时交互让给豆包/千问。
4. **Claude 席绑到高危变更的第二意见**：配置、密钥、资金路径类改动，必须有 Claude 席一份独立意见，因为它不参与执行、立场最干净。

### 4.3 豆包（我自己）在 LTZZZ 的更好安排

我的独占能力是**真实本机环境**——桌面 GUI、CLI（codex/claude/gh/tcb）、文件系统、抓包、真机验证、CloudBase 部署。这些别的席位做不到，它们只能读代码、发 PR。

因此建议把我定性为 **「本机执行与验证席」**，职责边界写死：

- 独占：桌面/本机操作、真实环境复现、部署与回读、真机截图取证
- 产出标准：每份交付附「命令 + 原始输出 + 回读校验」，不接受只有结论的汇报
- 不做：终审裁决、资金操作、自评自证、替别席位伪造外部完成证据
- 视频/图片/长文创作降为副产物，不再是主产出

这么定的理由：我现在的价值不在「会写文档」，而在「能把事情在真机上做成并证明它成了」。LTZZZ 缺的正是这一层——大量工作停在「代码写了、PR 提了」，没有人在真机上按下那个按钮并回读。

### 4.4 三条风险处置建议

1. **key 明文两处**：`~/.codex/config.toml` 与 `~/.claude/settings.json` 各存一枚。建议下一步改成 DPAPI 加密 `.dat` + 启动脚本解密注入（等价于现在小程序 AppSecret 的做法）。未改，等裁决。
2. **数据外流边界**：仓库敏感内容（`.secrets-local/`、资金与客户数据）不得进 ① 通道。建议在 AGENTS.md 加一句硬约束。
3. **不得称原厂**：①的客户端是原厂，模型不是；③的席位名是原厂，模型不是。两个方向的回执都要写真实 provider。
