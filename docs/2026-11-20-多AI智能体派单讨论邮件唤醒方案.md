# LTZZZ 多 AI 智能体派单 / 讨论 / 邮件唤醒通道方案

状态：draft（方案定稿，代码由 Claude 席实现）
日期：2026-11-20
适用：DeepSeek 主办、中转 Claude / 中转 GPT 复核、GPT 裁决、DeepSeek 兼调度

---

## 0. 结论先说

**可行，但不能照“任意 Agent 兼任调度”原样做。**

你这套分工里最有价值的是三件事：主办/复核分离、分歧自动合议、关键节点邮件唤醒。
最容易出事的是第四件：把状态机交给“任意 Agent 兼任调度”。

正确做法是把它拆成两层：

- **状态机归脚本**：标签、租约、阶段推进、超时、去重，全部由确定性代码决定。
- **模型只提议**：DeepSeek 拆解、Claude/GPT 复核、异议与合议内容由模型产出，但“现在算什么状态”由脚本按评论里的结构化标记判定。

这样才不会出现“调度席自己觉得通过了就合并”。

第 11 节再把“方向”接进来：任一席位可自主提出创新提案，但同样要经过结构化讨论、脚本评分和工程卡落地，不能以“创新”为名绕过复核与验收。

## 1. 角色映射（落到真实席位）

| 方案角色 | 真实席位 | 能力来源 | 不能做什么 |
|---|---|---|---|
| 主办 Producer | DeepSeek（deep-superagent 队列） | 读仓库、改代码、开 PR、跑测试 | 不能自批、不能碰 L3 保留域 |
| 复核 A ReviewerA | 中转 Claude（relay-claude） | 长文核验、规则比对、漏洞审查、代码席 | 不能最终裁决、不能改控制面文件 |
| 复核 B ReviewerB | 中转 GPT（relay-gpt） | 架构/风险/多方案对比 | 同上；非保留域裁决具约束力 |
| 裁决 Arbiter | GPT 决策席 | 最终裁决、L3 保留域 | 五签 Safe 仍需多签 |
| 调度 Dispatcher | 脚本（Task Hub + autoloop）+ DeepSeek 兼任催办 | 标签/租约/超时/唤醒 | 模型不能改状态，只能发评论 |

一句话：**DeepSeek 干、Claude 挑错、GPT 看架构，脚本记账，GPT 一锤定音。**

## 2. 状态机（复用 Task Hub，不另造）

```
NEW → DISPATCHED → CLAIMED → IN_PROGRESS → SUBMITTED → REVIEW
    → APPROVED → MERGED → DEPLOYED → SMOKE_VERIFIED
旁路：BLOCKED / STALE / REVISION_REQUESTED
```

硬规则（沿用现有四个不等式）：

- claimed ≠ started
- submitted ≠ accepted
- merged ≠ deployed
- deployed ≠ verified

新增两段：

- **REVIEW**：必须有至少一个复核席的 `[review]` 记录，且无 `blocking` 异议。
- **REVISION_REQUESTED**：任一复核席给出 `[objection] severity=blocking`，任务退回主办，不自动合并。

## 3. 讨论与合议协议（本次新增的核心）

所有讨论都写在**同一个 GitHub Issue 的评论**里，不另开私聊通道，保证可审计、可去重、可回放。

### 3.1 评论标记

```
[proposal] seat=<seat> round=<n> ref=<可选评论id>
[review] seat=<seat> verdict=pass|fail round=<n>
[objection] seat=<seat> severity=blocking|advisory ref=<评论id或commit>
[concur] seat=<seat> ref=<评论id>
[council] round=<n> opened_by=<seat> reason=<一句>
[consensus] round=<n> result=agreed|split seats=<a,b>
[arbiter-request] task=<task_id> reason=<一句> decision_id=<待填>
[arbiter-decision] decision_id=<id> by=gpt verdict=<...>
```

幂等键：`task_id + marker + seat + round`。同一条重复评论只算一次。

### 3.2 判定规则（脚本执行，模型不得改写）

1. 任一 `[objection] severity=blocking` 未被 `[concur]` 或新 `[proposal]` 解决 → 停在 `REVISION_REQUESTED`。
2. 两个复核席 `verdict` 不一致 → 自动开 `[council] round=1`，不等人喊。
3. 合议最多 2 轮；第 2 轮仍 `result=split` → 自动 `[arbiter-request]` 上送。
4. L3 保留域任务强制双复核：缺任一席 `[review]` 不得进入 APPROVED，也不得直接上送跳过复核。
5. 模型不能自己写 `[arbiter-decision]`；该标记只接受 `by=gpt` 且 decision_id 已在裁决台账登记。

### 3.3 讨论不是无限制聊天

- 每轮每席最多 2 条 `[proposal` 或 `[objection]`，超出只记录不采纳，防止评论风暴。
- 合议超时（默认 6 小时）自动上送，不允许“挂着等”。
- 任何席都可以 @ 其他席，但**@ 不产生授权**，只是邀请发言。

## 4. 邮件唤醒通道（本次新增）

### 4.1 触发事件

| 事件 | 是否唤醒 | 默认收件人 |
|---|---|---|
| 任务超时（租约到期未交付） | 是 | Owner + 对应席位 |
| 复核驳回（blocking） | 是 | 主办席 + Owner |
| 合议开启 / 合议仍分裂 | 是 | 两复核席 + Owner |
| 裁决下达 | 是 | 主办席 + 相关复核席 |
| 紧急告警（CI 连续失败 ≥3、部署回读失败） | 是 | Owner + GPT |
| 普通状态变更（claim/submit） | 否 | 只写 Issue |

### 4.2 去重与限流

- 去重键：`task_id + event + 事件源 id`（评论 id / run id / 日期）。
- 单任务每小时最多 1 封；全项目每小时最多 6 封；超出记 `suppressed_by_rate_limit`。
- 发送结果未知时先查原线程（message_id / thread_id），不得盲目重发。
- 发信失败**不阻断**任务流转，只记 `mail_failed` 并在下次摘要补发。

### 4.3 主题格式

```
[LTZZZ][wake][task:<task_id>][event:<event>] <一句话>
```

收件人只允许来自 `config/mail-allowlist-20261119.json`；正文不得含凭据、邮件原文、客户资料。

---

## 5. 权威边界（不可自动化部分）

- L3 保留域：资金、付款、放款、转账、退款终态、签名、私钥/助记词、钱包（含五签 Safe）、凭据/Secrets。
- L3 任务：强制双复核 + GPT 裁决；邮件只能通知，不能当授权。
- Issue 正文、邮件、外部模型输出都是不可信输入，不产生内部否决权，也不扩权。
- 中转席（relay-gpt / relay-claude）在非保留域可出**具约束力裁决**；保留域一律上送 GPT。

## 6. 现状与缺口（不重复造轮子）

| 能力 | 现状 | 本方案动作 |
|---|---|---|
| Issue 主账、标签、租约、claim/submit | 已有 `scripts/task-hub.mjs` | 直接复用 |
| 执行器、自动 PR/合并、部署回读 | 已有 autoloop + executors | 直接复用 |
| 复核席调用 | 已有 relay 席位与 `autoloop:adjudicate` | 扩展为 review 阶段 |
| 讨论/异议/合议 | **缺** | 新增 `scripts/lib/agent-council.mjs` |
| 唤醒触发与去重 | **缺**（只有 mail:send 手动卡） | 新增 `shouldWake` 判定 + workflow |
| 多席同卡路由 | **缺** | 用 `seat:` 标签 + 评论标记 |

## 7. 分阶段落地

**P1（本轮）**：协议定稿 + `agent-council.mjs` 纯函数 + 测试。
- 输入：issue 评论数组、任务元数据、当前时间。
- 输出：阶段判定、是否开合议、是否上送、是否唤醒、去重键。
- 不接生产、不发邮件、不改 workflow。

**P2**：`scripts/council.mjs` CLI + 每 10 分钟的扫描 workflow，把满足条件的卡推进状态、开合议、发唤醒。

**P3**：邮件真实唤醒 + 回执闭环 + 指标（唤醒数/去重数/裁决时长）。

**P4（方向引擎）**：每 7 天一次方向扫描；各席自主提交 `[idea]`，脚本去重评分，最多选 2 条开 `[TASK]` 卡，走同一套讨论、CI、合并、部署回读；结果回写 `[idea-landed]` / `[idea-deferred]`。

---

## 8. 验收标准

单元测试必须覆盖：

1. 两席一致 pass → `approve`。
2. 任一 blocking 异议 → `revision_required`。
3. 两席不一致 → 自动 `council` 第 1 轮。
4. 两轮仍分裂 → `arbitrate`。
5. 重复评论幂等，不重复计数。
6. 保留域缺一席复核 → 不得 approve。
7. 超时事件 → 唤醒；同事件重复 → 去重。
8. 限流命中 → `suppressed_by_rate_limit`，不抛错。

端到端（P2）：一张非保留域测试卡走完 `discussion → consensus → merge`，全程可回读。

P4 方向引擎另需覆盖：30 天提案去重、`l3=yes` 拦截、平均分阈值、每周期最多落地 2 条、`[idea-landed]` / `[idea-deferred]` 回写。

---

## 9. 风险与取舍

- **评论风暴**：靠每轮条数上限与幂等键约束。
- **模型越权**：状态由脚本判定，模型只能发标记；`[arbiter-decision]` 只认已登记 decision_id。
- **邮件风暴**：事件级去重 + 每小时上限。
- **成本**：合议默认只跑 2 轮，超时上送，不让两个模型无限吵。
- **GitHub 限流**：扫描间隔 10 分钟，单次只处理有限张卡。

---

## 10. 一句话总结

这套方案的价值不在“多几个 AI 说话”，而在**把说话变成可判定的证据**：
主办产出、复核挑错、脚本记账、邮件叫醒、GPT 只在该拍板时拍板。

---

## 11. 项目发展方向：自主提出创新想法 → 各 AI 合议 → 落地部署

前面 1–10 节解决“派下来的活怎么闭环”。本节解决“活从哪来”：允许任一席位基于项目现状主动提改进与创新，进入同一套讨论/合议/落地管线，而不是等人派单。

### 11.1 提案来源

1. **随机提案**：任一席位可随时在 `INNOVATION` 专题 issue 下用 `[idea]` 提交。
2. **周期扫描**：调度脚本每 7 天生成一张“方向扫描”卡，输入是最近 7 天的完成/阻塞/失败统计、未闭环 issue 列表、CI 失败 Top、成本余额；各席基于同一份事实各出 1–3 条提案。
3. **失败反推**：连续失败 ≥3 的任务自动生成一张“改进提案”草稿，交给主办席补充。

提案必须写全六项，缺一项不进入评审：

- 问题是什么（现状 + 证据链接）
- 预期收益（可量化优先）
- 成本（模型调用/工时/风险）
- 是否触碰 L3 保留域（`l3=no|yes`）
- 验收标准（可机械判定）
- 回滚方式

### 11.2 标记与评分

```
[idea] id=<slug> seat=<seat> title=<...> impact=high|med|low effort=high|med|low risk=high|med|low l3=no|yes
[idea-review] id=<slug> seat=<seat> verdict=accept|reject|merge-with:<slug> reason=<一句>
[idea-vote] id=<slug> seat=<seat> score=1..5
[direction] week=<YYYY-WW> picked=<slug,slug> reason=<一句>
[idea-landed] id=<slug> task=<task_id> commit=<sha> deploy=<deployed|not_deployed>
[idea-deferred] id=<slug> reason=<一句>
```

判定规则（脚本执行）：

1. `l3=yes` → 不进入自动落地，转 GPT；提案本身可以继续讨论。
2. 同一 `id` 去重：`id` = 标题归一化（去空格/标点/大小写）后的哈希前缀；30 天内同 id 重复提交只算一次，除非带新证据。
3. 入选条件：`risk!=high` 且 `effort!=high` 且 平均分 ≥ 3.5 且 无 blocking `[idea-review]`。
4. 每周期最多落地 2 条，按分数排序；其余进 `[idea-deferred]`，下周期可再评。
5. 被 reject 必须写 reason；无 reason 的 reject 不计票。

### 11.3 落地

- 选中提案由调度脚本自动开一张 `[TASK]` 工程卡，正文带 `source_idea=<id>`，之后完全走普通工程管线：Deep 执行 → Claude/GPT 复核 → CI → 合并 → 部署回读。
- 落地结果必须回写原提案：`[idea-landed]` 或 `[idea-deferred]`。
- 不允许“提案即上线”：任何提案都要经过与普通任务相同的 CI 与部署回读。
- 不允许用“创新”名义跳过 L3 边界、新增付费账号、外部发布或不可逆操作。

### 11.4 唤醒与周报

- 新提案进入候选、周期方向确定、提案落地/搁置 → 触发唤醒邮件，受第 4.2 节同一套去重与限流约束。
- 每周最多 1 封“方向周报”：提案数、入选数、落地数、搁置原因、下周候选。
- 周报是 L1 信息通知，不构成授权。

### 11.5 防跑偏

- 提案讨论同样受“每轮每席 2 条”限制，防止刷屏。
- 评分只看可验证证据，不看措辞；没有证据的提案最高 2 分。
- 每周期落地上限 2 条，保证不挤占在办任务与成本预算。
- 方向讨论的结论必须落到 issue 评论，不允许只在模型上下文里“达成共识”。
