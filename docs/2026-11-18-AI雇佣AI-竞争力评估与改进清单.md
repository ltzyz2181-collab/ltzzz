# AI 雇佣 AI：市场竞争力评估与改进清单（2026-11-18）

依据：仓库内现有代码、回执与线上状态。凡未取得证据的判断，本节标为「判断」而不是事实。

## 一、先说结论

1. **技术上有真差异化，商业上还没有竞争力。** 差异化在「验收是机器跑出来的 exit code，不是模型自述」和「资金/签名意图直接拒绝并上交裁决」这两条；竞争力缺的是需求侧：现网真实收入 **0**，外部客户订单 **0**，小程序现网 9 条订单全部 `pending`。
2. **现在能卖的还不是「AI 雇佣 AI 市场」，是三项人工交付服务**（¥9.90 / ¥14.90 / ¥19.90，24 小时内交付）。「AI 雇 AI」是仓库内闭环（`ops/hire`、`scripts/hire-phase1.mjs`），`amount_usd: 0`，没有真实付薪。
3. **最该做的不是再加功能，是把已有的可验证交付做成一次真实成交。** 现在缺的是第一个付费客户和一份可公开的验收报告，不是第四个 SKU。

## 三、市场位置：我们和谁在同一个格子

把「AI 接活」拆成三层看，LTZZZ 目前只占住第三层的一小块：

1. **通用 Agent 分发层**（GPT Store / MCP 生态 / 各类 agent 目录）：拼流量、拼账号体系。我们没有流量，不占优势，也不该在这里拼。
2. **Agent 市场层**（Fetch.ai、Virtuals、Olas 一类，以及各类「AI 接单」平台）：拼双边网络效应、质押与仲裁。我们双边都是 0，贸然进去只会变成又一个空货架。
3. **交付可信层**（验收、对账、拒绝权、可审计回执）：这是我们的结构性优势。市场上多数 agent 平台的验收是「模型说自己做完了」，我们的验收是「机器跑的命令退出码」，并且资金意图在合同层就被拒。

**判断**：短期内不要在 1、2 层和大平台正面竞争；把第 3 层做成可展示、可收费、可复用的能力，再回头去接 1、2 层的订单。

## 四、优势（可辩护的三条）

1. **验收不可自证**：`gateOutcome()` 只认单条 `node` 命令的真实退出码，不接受席位自述；闸拒绝 shell 元字符，防止一次验收塞进多个动作。
2. **拒绝权在合同层**：命中资金/签名/钱包/Safe/放款/凭据/生产写的雇佣单直接 `needs_owner_decision`，闸根本不执行（对抗样例 `HIRE-SAMPLE-20261116-02` 已验证）。
3. **账本可复算**：只追加 JSONL，每条含 `order_sha256`、`receipt_sha256`、`paid:false`、`amount_usd:0`，第三方可按哈希复算，不依赖平台后台。

## 五、劣势（不补就永远停在演示）

1. **需求侧为零**：没有真实付费客户，没有一份可以公开的客户验收报告。
2. **没有争议处理**：验收失败之后谁仲裁、怎么扣款、怎么申诉，代码里没有。
3. **没有定价机制**：三个 SKU 是拍出来的价格，不是按验收复杂度或工时算出来的。
4. **没有第三方 AI 雇员**：现在的「雇员」全是自家席位，等于自己雇自己，市场叙事不成立。
5. **交付产物仍靠人工**：小程序 README 已如实写明，自动化的只是订单状态，不是交付内容。
6. **重复入口太多**：小程序、WEP3 market、Gumroad、uGIT/uUmit 各有一套价格和状态，客户看到的是不一致。

## 六、改进清单

### P0（两周内，直接决定有没有第一笔真实收入）

1. **把 `order-deliver` 在真机上跑通一次**：页面调用已接好（`pages/orders/index.js` 按订单号上传），云函数与 17 项测试就绪，缺的是真实付费单上的一次 `intake → deliver` 全流程验证，以及 `ADMIN_OPENIDS` 在云函数环境变量里配置到位的回读证据。
2. **做一份可公开的验收样例**：用「交付验收核对」服务对一份公开材料跑一遍，产出带哈希的报告，放到 `products/delivery-check/` 作为样例，客户能看到买到什么。
3. **统一价格口径**：小程序、WEP3、Gumroad 三处价格与交付时限对齐到一张表，避免同一个服务三个价。

### P1（一个月内，把「AI 雇 AI」从演示变成可复现流程）

4. **接一个真实外部 AI 雇员**：用已有 uumit/uGIG 账号接一单，把「雇佣单 → 验收闸 → 只增账本」跑在真实订单上，哪怕金额是 0.05 USDC。
5. **加争议分支**：验收 `refused` 之后要有 `revision_requested` 和 `escalated` 两个状态，以及对应的回执字段，不能只有 accepted/refused 二元。
6. **补成本核算**：每单记录模型调用次数与 token，算一次真实毛利；没有毛利数据就无法定价。

### P2（季度内，形成可对外讲的差异化）

7. **公开验收报告格式**：把 `delivery-check` 的输出做成固定 schema，允许第三方复算哈希。
8. **第三方席位注册表**：外部 AI 雇员要能被登记、被复核、被替换，而不是写死在代码里。
9. **一张对外一页纸**：只讲「机器验收 + 拒绝权 + 可复算账本」三件事，不讲宏大叙事。

## 七、一句话回答「有没有优势」

- **有技术优势**：验收与拒绝权的设计比多数 agent 市场更硬，且已有可运行代码和测试。
- **没有市场优势**：零客户、零收入、零外部雇员，任何「领先」说法都还撑不住。
- **最短路径**：先用现有三项服务做成一次真实成交并公开验收报告，再把 Phase1 的验收闸接到这笔真实订单上。

## 八、Deep 分流与团队执行现状（2026-11-18 实测代码口径）

### 链路

push 到 main 且改动 `ops/deep-superagent/{tasks,decisions}/*.json` → `deep-superagent-queue.yml` 的 `verify`（`node --check` + 队列测试）→ `consume` → `run-deep-superagent-queue.mjs` 只取本次新增的 A 卡 → `POST /v1/jobs/*` → Cloudflare Durable Object `DeepTask.alarm` → deepseek 规划 1–3 席 → 原生席（doubao / qianwen / kimi / grok）经 service binding 调用、gpt / claude 只走 relay 执行席 → content gate → deepseek 独立复核 → `completed_pending_external_acceptance` 或 `needs_gpt_decision`。

### 已改好的三处（本轮）

1. **批量消费**：一次 push 由「同类 1 张」放宽到「同类 3 张、合计 6 张」，`consume` 超时 12 → 25 分钟。这是原来最堵的一处：团队有四张卡就得 push 四次。
2. **单席失败不再整单作废**：失败席记为 `unjudged`，成功的产物、回执、哈希保留，继续独立复核，卡片落 `needs_gpt_decision`；全部席位失败才 `blocked`。
3. **豆包/千问 504**：换快档 + 关思考，减少席位超时。

### 仍然不能「全自动」的地方（不是 bug，是有意的人工边界）

1. **裁决不自动生成**：卡片进 `needs_gpt_decision` / `blocked` 后，没有自动生成裁决卡、也没有自动发邮件唤醒（`escalation.email_sent` 恒为 `false`）。要么 GPT 席位写裁决卡，要么人手动发。
2. **终态不自动置位**：`accepted` / `platform_accepted` / `deployed` / `paid` 四个字段没有任何自动写入路径，只能由真实回读或人工确认填。
3. **对外动作仍关闭**：`external_submissions_enabled=false`、`financial_execution=false`，Deep 席位不能对外投稿、接单收款或动资金。
4. **客户验收必须人做**：机器门只看 exit code，但「这个交付客户认不认」不是 Deep 能自己宣布的。

### 席位安排：合理，但有一处结构性弱点

- 合理：规划用 deepseek（长上下文、便宜），执行用 4 个原生席 + 2 个 relay 席，relay 明令只执行不决策；独立复核要求 `independent_of_worker_providers`。
- **弱点**：**规划者和复核者都是 deepseek**。`independent_of_worker_providers` 只保证复核席不在 worker 集合里，没保证复核席不是规划席本身。等于「自己出题、自己判卷」。
- 建议（P1，未改，因为会动执行语义需要单独回归）：deepseek 规划的任务，复核改用 qianwen；或要求 `reviewer.provider !== planner.provider`。改之前先补一条「同源自审」的对抗测试。
