## 1. P1-1：USDC 余额读取

### 1.1 现状

`rpc.mjs:152` 批量调 `eth_getBalance`，读出的是链原生币；`ONCHAIN_DECIMALS = 18` 写死；`balance-view.mjs:140` 直接拼 `${amount} ETH`。所以"ETH 余额"与"USDC 余额"目标不一致，但当前是自洽的（读什么显示什么），不是 bug 而是口径缺口。

### 1.2 目标接口

`readOnchainBalance({address, rpcUrl, token, expectChainId = '8453', fetchImpl, timeoutMs, headers})`

- `token` 缺省 → 走现有原生币路径，字段不变（`wei`、`decimals: 18`、`balance_source:'onchain_rpc'`）。
- `token` 提供 → 走 ERC-20 路径，返回：

```json
{"status":"ok","asset":"USDC","token_address":"0x…","decimals":6,"units":"1234567",
 "amount":"1.234567","chain_id":"8453","block_number":"…","balance_source":"onchain_rpc","read_at":"…"}
```

- ERC-20 路径**不再输出 `wei` 字段**，避免下游把 token units 当原生币；新字段统一叫 `units`。

### 1.3 调用设计（全部走 `client.batch`，方法均已在只读白名单）

1. `eth_chainId` → 必须等于 `expectChainId`（默认 Base 8453）。不等 → `status:'unavailable', reason:'chain_mismatch'`，**不返回数字**。
2. `eth_call` → `to: token.address, data: 0x70a08231 + 左补零到 32 字节的 address`（`balanceOf(address)`）。
3. `eth_call` → `data: 0x313ce567`（`decimals()`）。
4. `eth_blockNumber`（用于记录读取高度）。

校验链：
- `token.address` 必须过 EIP-55（含大小写校验位）或全小写 + 长度 40 的十六进制；不合格直接 `invalid_token_address`，不发请求。
- `balanceOf` / `decimals` 结果必须是 `0x` 十六进制且长度 ≤ 32 字节；`decimals` 必须 `0 < n <= 36`，缺失或非法 → `token_decimals_unreadable`，**不回落 6**。
- 金额换算复用 `unitsToAmount`（十进制字符串），禁止浮点。

### 1.4 本地约束（防止 `eth_call` 被当成通用探针）

`createReadOnlyRpc` 保持通用，但在钱包侧封装一层 `callTokenView`：只接受 `to === token.address` 且 `data` 命中白名单选择器（`balanceOf`、`decimals`），其余一律抛 `unauthorized_token_call`。这样即使调用方传错，也打不到任意合约。

### 1.5 配置

- 链 ID 与合约地址只从配置读取，不写死在代码路径里：
  `agent-wallet/wallet/tokens.json`（新文件，不含私钥，只有 `{chainId, asset, address, decimalsHint}`）；
  命令行 `--token <symbol>`，默认不启用 ERC-20 路径（保持现有默认输出不变）。
- Base USDC 合约地址作为**文档示例**写在 README，不进默认运行路径——原因：地址写错一位的代价是读到别的代币余额，属于典型的常量抄错风险，必须在测试里用校验位断言。

### 1.6 测试清单（`__tests__/rpc.test.mjs` 扩展）

| 用例 | 断言 |
| --- | --- |
| 原生路径不回归 | `token` 缺省仍返回 `wei`，`decimals` 18，输出与改前逐字段相等 |
| USDC 正常读取 | 假 fetch 返回 `0x…` + `decimals=6` → `units`/`amount` 正确，`asset:'USDC'` |
| 链不符 | `eth_chainId` 返回 1 → `unavailable/chain_mismatch`，**无** `units` 字段 |
| decimals 读失败 | 返回 `0x` 空 → `unavailable/token_decimals_unreadable`，不出现 6 |
| 合约地址非法 | 传 39 位或含非法字符 → `invalid_token_address`，且 fetch 未被调用（断言调用次数 0） |
| 越权选择器 | 传 `0xa9059cbb`（transfer）→ `unauthorized_token_call`，fetch 未调用 |
| 零余额 | `0x0` → `status:'ok'`, `units:'0'`, `amount:'0'`（与"读不到"区分） |
| 格式器 | `formatBalanceView` 对 ERC-20 视图输出 `onchain: ok 1.234567 USDC`，不再出现 `ETH` |

## 2. P1-3：`appendEvent` 增量校验

### 2.1 现状与成本

`appendEvent`（`core.mjs:815`）每次调用都执行：`loadLedger`（整文件读 + 逐行 JSON.parse）→ `verifyLedger`（逐记录重算 `hashEventRecord`）→ 遍历全部事件查幂等键 → `foldBalances`（全量折叠）。N 次追加累计 O(n²)。

### 2.2 设计：受校验的头部快照缓存

新增 `verify-state.json`（与账本同目录，mode 0600），内容：

```json
{"schema":"ltzzz.wallet.verify.v1","ledger":"wallet/ledger.jsonl","bytes":12345,
 "count":N,"head":"<最后一条 hash>","prefix_sha256":"<前 bytes 字节的 sha256>",
 "folded":{"accts":{...},"frozen":{...},"byAsset":{...}},"idempotency":{"keys":{...}}}
```

`appendEvent` 新流程（持锁后）：

1. `open` 账本文件，读全量 raw（一次顺序 I/O，O(n) 字节，不逐行 parse）。
2. 读缓存；若缓存存在且 `count <= 文件记录数` 且 `sha256(raw[0..bytes]) === prefix_sha256` 且 `raw` 在该 `bytes` 处正好是换行边界：
   → **快速路径**：只 parse 第 `count+1` 行之后的增量记录，逐条做 `seq/prevHash/hash/字段` 校验（与 `verifyLedger` 同一套 `validateStoredEvent`），折叠只叠加增量事件，幂等键只在增量里查 + 在缓存键表里查。
3. 任一条件不满足（缓存缺失、prefix 哈希不符、字节边界不对、增量里出现 `seq` 跳号、文件比缓存短=被截断）→ **回退全量**：执行现有 `loadLedger + verifyLedger + foldBalances`，并把新快照写回缓存（fail-closed，绝不因缓存异常而跳过校验）。
4. 追加成功后以原子写更新缓存：写 `verify-state.json.tmp` → `fsync` → `rename`；`bytes/count/head/prefix_sha256/folded` 取追加后的值。

缓存不参与任何对外读取：`verifyChain`、`deriveBalance`、`readEvents`、`assertChainValid` 一律仍走全量校验，缓存只在 `appendEvent` 的写入路径上作为"已验前缀"的加速凭证。

### 2.3 失效语义（必须写成测试）

| 场景 | 期望 |
| --- | --- |
| 缓存文件被删/损坏 JSON | 回退全量，结果与无缓存完全一致 |
| 账本中间一行被改一个字节 | prefix 哈希不符 → 回退全量 → `ledger_corrupt`，拒绝追加 |
| 账本被截断（少最后一行） | 文件比缓存短 → 回退全量 → `seq` 缺号报错，拒绝追加 |
| 账本被整段替换但保持自洽 | prefix 不符 → 回退全量 → 校验通过（因为自洽）→ 允许追加；此时 `expectedHead` 外部锚定仍是唯一防线，方案不掩盖这一点 |
| 缓存伪造 `head/folded` | prefix 哈希由文件真实字节算出，伪造缓存无法匹配 → 回退全量 |

### 2.4 测试清单（`__tests__/ledger.test.mjs` 扩展）

1. **等价性**：构造 30 条事件的 fixture，分别用"全量路径"（删缓存）与"缓存路径"各追加 20 条，断言两条链的 `hash/seq/prevHash/head` 逐条相同，`verifyChain` 均 `ok`。
2. **等价错误语义**：余额不足的 debit 在两条路径上抛同一个 `insufficient_available`，且账本字节不变。
3. **缓存失效三例**：改动中段字节、截断末尾、删缓存 → 行为分别为"拒绝 + `ledger_corrupt`"、"拒绝 + `seq_mismatch`"、"正常追加"。
4. **性能回归（不测墙钟）**：注入计数器统计 `hashEventRecord` 调用次数，追加 100 条断言总调用次数 ≤ 100 + 常数项（证明不再随 N 线性叠加），而不是断言耗时。
5. **幂等**：同一 `idempotencyKey` 重复追加返回 `duplicate:true`，缓存不产生第二条记录。

## 3. P1-2：哈希链签名（不落代码，待裁决）

现状：`hashEventRecord` 只做内容哈希，`prevHash` 串成链；整段重写并重算哈希可自洽。缓解手段是 `expectedHead` 外部锚定（README 已承认）。

三个选项，代价不同：

- A. **本地密钥 + 每条记录 detached 签名**：需要新增密钥文件与其生命周期管理，越"资金/签名边界"，模型席不得自行实施。
- B. **保持无签名，强化外部锚定**：定期把 `head` 发布到不可篡改位置（GitHub commit / 公开时间戳），代码只增加"锚点比对"接口，不引入密钥。
- C. **不改账本，另建只追加的镜像 + 每日对账**：把链头写入另一个写一次读多处，靠两处比对发现重写。

建议：先 B（零密钥、可立即做、成本最低），把 A 留给有 KMS 或硬件签名的场合。
