# 对话部署话术模板（2026-11-16）

用途：把「切 main → 真实小改动 → 跑测试 → push → 回读 Actions」固定成一句话，桌面 Codex 对话框里改一个词就能用。首次闭环证据见 `docs/2026-11-16-桌面Codex接入DeepSeek实测与model_provider落地.md` 第九节（commit `fdf00a3c`）。

## 一、一句话版（日常用这个）

```
在 ltzzz-repo 里改 X，跑 <测试命令>，通过后 commit 并 push 到 main，然后回读本次 push 触发的 Actions 结果贴给我。
```

把 `X` 换成具体改动，`<测试命令>` 换成该目录既有测试命令（见第四节）。不要用「优化一下」「修一下」这类含糊词，Codex 会反问，反而多一轮。

## 二、完整版（涉及多个文件或需要回执时用）

```
任务：在 ltzzz-repo 完成 <改动描述>
Task ID：<仓库约定的 Task ID>
分支要求：从 origin/main 拉干净 worktree（不要动我当前工作树），完成后 push origin HEAD:main，不用 --force、不 rebase 别人的提交
测试要求：跑 <测试命令>，必须 exit 0；失败就保留失败输出再改方法，不要直接强推
提交要求：commit message 保留 Task ID，并注明状态（草稿/已测试/已部署）
完成后：回读 push 触发的 Actions run（名称/结论/链接），并说明改了哪些文件、几行、测试结果
越界禁止：不改支付与资金语义、不动 allowedAgents、不碰凭据、不做生产写
```

## 三、必须先满足的三个前置条件

1. **分支在 main**。桌面仓库常停在 `feat/order-closure` 且有未提交改动；在那种分支 push 不触发 main 的部署，也容易把用户的半成品混进来。正确做法：`git worktree add --detach <临时目录> origin/main`，在 worktree 里干活。
2. **Task ID 有了**。仓库约定 commit/PR 保留 Task ID 并区分草稿/已测试/已部署/已交付。没有就先用一句话描述，让 Codex 在 commit 里写明"无 Task ID，owner 口头指派"。
3. **harness 先跑**。按 `AGENTS.md`，正式动手前执行 `node scripts/harness.mjs before receipt,model_output,input_hash,external_platform`，并把实际改动写进已有回执。

## 四、测试命令怎么填

- 单个测试：`node --test scripts/tests/<name>.test.mjs`
- harness 相关：`node --test scripts/tests/lessons.test.mjs scripts/tests/reflection-harness.test.mjs scripts/tests/ltzzz-skill.test.mjs scripts/tests/ans-cycle.test.mjs scripts/tests/workpool.test.mjs`
- 只是文档：`git diff --stat` + 确认 Markdown 链接不断（没有自动校验就明说"未跑自动化测试"）

## 五、回读与验收（push 之后必做）

1. `git ls-remote origin main` 回读 SHA，确认与本地 commit 一致。
2. `gh run list --limit 5 --json name,status,conclusion,headSha,url`（云主机有 gh；**桌面没有 gh**，桌面只能开网页看）。
3. 逐条核对：run 的 headSha 是否等于本次 commit、conclusion 是否 success；有 failure 要写明是哪条 workflow、是否与本次改动相关。

## 六、失败时的处理口径

- push 被拒（non-fast-forward）：先 `git fetch`、在干净 worktree 里 rebase 到 origin/main，再重试；**不 force push**。
- 测试失败：保留失败输出与文件现状，记录实际失败原因，再改方法；不要把"改到能过"当成唯一目标而绕过断言。
- Actions 失败但与改动无关（例如既有定时任务）：如实分开写，不混入结论。

## 七、分流规则（owner 2026-11-16 决定：部署类任务可分一点给桌面）

| 任务类型 | 执行席位 |
|---|---|
| 仓库内改代码、补测试、commit、push main、回读 CI | 桌面 Codex 对话框 |
| 需要密钥、CI 手动触发、跨仓库操作、发信、生成回执文档 | 云主机（本席） |
| 生产写、支付/资金动作、签名与 Safe、凭据轮换 | 不做（按既有边界，交 GPT 席位裁决） |

理由：桌面有真实工作树与 GUI，改代码最快；云主机有 `gh`、密钥与 agently-cli，适合触发与取证。桌面缺 `gh`，所以"手动 dispatch"这类动作仍回云主机或网页。
