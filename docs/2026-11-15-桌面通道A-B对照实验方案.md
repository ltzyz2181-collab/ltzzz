# 桌面通道 A/B 对照实验方案（2026-11-15）

## 目的

回答一个具体问题：**Codex / Claude Code 这层"壳"到底比裸 API 多做了多少**。不靠感觉，靠三组同一任务的实测数据。

## 实验任务（三组必须完全相同）

在临时目录（不动仓库、不动桌面项目）里准备同一份起点代码：

- `sum.mjs`：导出 `sum(nums)`，只做求和，无参数解析。
- `sum.test.mjs`：`node --test`，现有 2 条用例（正数、空数组）。

任务描述（原文逐字复用，不许改写）：

> 给 sum.mjs 加一个命令行入口，支持 `--offset <整数>`，把 offset 加到结果上；默认 0。补两条测试：带 `--offset 5`、带非法 offset 时非零退出码。跑 `node --test` 必须全绿。只改这两个文件。

## 三组

| 组 | 做法 | 要记录的关键点 |
|---|---|---|
| A 裸 API | 把同一段任务描述一次性发给 `api.deepseek.com/v1/chat/completions`（model=deepseek-chat），拿到文本答案后**由人把代码贴进文件再跑测试** | 模型是否给出可直接落盘的完整改动；人工粘贴/修补了几次 |
| B Codex | 在临时目录里用 Codex CLI 实跑同一任务描述 | 是否自己读写文件、是否自己跑测试、是否自己看报错再改 |
| C Claude Code | 用 `claude` CLI 实跑同一任务描述（后端为 deepseek-chat） | 同上；若装不起来则如实记为"未取证"，不得用 B 的结果顶替 |

## 指标（每组都填）

1. **成功率**：`node --test` 最终是否全绿（是/否）。
2. **耗时到可运行**：从发出任务到测试全绿的墙钟秒数。
3. **改动文件数**：实际被修改的文件个数，以及是否碰到任务外的文件。
4. **人工介入次数**：人为贴代码、改语法、修路径、重发提示的累计次数。
5. **token 用量**：prompt / completion（裸 API 能读到；CLI 侧按会话日志或不计，写"未取证"）。
6. **失败模式**：报错类型、是否自我纠正、是否谎报完成。

## 判定规则（事先定好，避免事后找理由）

- 若 B/C 的成功率高且人工介入为 0，而 A 需要人工粘贴 → 壳带来的是**工程执行力**增量，可定量写成"少 N 次人工介入"。
- 若 B/C 成功率与 A 持平、只是自动化 → 壳只省手工，不提升解题质量，模型能力仍等于 DeepSeek。
- 若 B/C 因协议不兼容（DeepSeek 不吃 Codex 的 responses 流或 Claude Code 的工具协议）而失败 → 结论是**跨厂商套壳有适配损耗**，这与"能力增强"是两件事，必须分开写。
- 任何一组缺数据，就写"未取证"，不合并成平均分。

## 前置条件与当前阻塞

1. Codex 要能发请求，必须先把 `config.toml` 的 provider 切到 DeepSeek：见 `scripts/desktop-codex-provider-fix.py`（默认 dry-run，`--apply` 才写，自动备份并给回滚命令）。
2. Claude Code 侧 `claude` 命令当前不在 PATH，桌面只有安装包 `claude-1-30096-5.exe`；C 组能否成立取决于它能否在本机装起来并连上 `api.deepseek.com/anthropic`。
3. 三组都在 Windows 桌面执行；云主机上没有 Codex/Claude 客户端，**不要用云主机结果冒充桌面结果**。

- 若结论是"壳无增益"，照实写，不为了证明方案正确而修饰数据。
