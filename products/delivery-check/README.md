# LTZZZ 交付核验助手

把 AI 或外包的交付包与约定清单对照，列出缺文件、哈希不符、引文找不到及待复核项。第一版为本地工具，复用现有服务渠道，不新开 SaaS 或收集客户文件。

## 本轮可运行范围

1. 选一个自己有权处理的只读资料目录和 JSON 订单清单。
2. 检查文件是否存在、与约定 SHA256 是否一致，以及指定引文是否确实出现在指定本地文件中。
3. 导出机器可读验收报告。文件和正文不上传到 GitHub、模型或第三方服务器。

```sh
node products/delivery-check/check.mjs products/delivery-check/example products/delivery-check/example/order.json
```

自己的客户资料及导出报告请放仓库外，或已有忽略的 `.ltzzz-tools/` 私有工作目录。不要将真实订单材料推到公开仓库。运行期间根目录须由调用者控制并保持只读，不作为多租户公网上传服务器使用。

订单格式见 `example/order.json`。最多 50 个文件、每个 1 MiB、总计 5 MiB；仅扫描明确列出的文件，不递归搜索其他目录。拒绝路径穿越、绝对路径及符号链接；没有预期哈希时只提供指纹，不宣称完整性已经比对。

退出码：0 表示机械项无失败但仍待语义复核，1 表示需修正，2 表示输入无效/不可用。报告 `accepted=false`、`payment_authorized=false`；它不是订单放款接口。

**找到引文不表示引文支持主张。** 首版不联网验证链接、不判定事实含义、不充当专业鉴证；不能据此承诺“AI 已验真”。下一阶段沿同一产品添加有许可的来源语义复核和实际异源审阅，保留未核实项。

## 核心产品路线

目标客户：需要核对 AI/外包文稿、资料包和交付证据的小团队。核心交付是一份能定位问题的验收报告，现有“来源核对清单”和“交付包验收”作为同一产品的输入/报告模板，不再增加一批相似 SKU。

- 第一阶段：离线机械核验可运行；在自有合成样本上验证正例、缺件、错误哈希、缺引文、路径越界和“有引文但语义未验”。
- 第二阶段：从现有 uGIG/UUMit/WorkBuddy/微信取得一份真实、许可明确的订单；限定交付范围和成本，不重复上架或刷单。
- 第三阶段：复核、提交、买方接受和现金到账分别记录。UT、测试付款、内部雇佣不算客户现金收入。
- 产品能被接受并有重复付费需求后，才评估托管网页、模型 API 与付费扩容。当前 CLI 原型完成不等于已经上线收费或证明市场需求。
