## 已核实（通过）
1. **事务与告警同回滚**：`tx.put` 先校验、再写 ledger、再 `rearm`，全部在 `storage.transaction` 闭包内（helper L50-61）；测试 `rollback` 与 `alarm-failure` 在真实 workerd 中确认账本与告警都回到原值（测试 L73-85，且新单期限比旧单更早，若告警未回滚则会暴露）。
2. **最早期限**：`nextPaymentAlarmAt` 遍历全部未了结的 receipt/audit 期限取最小值（L20-33）；20 个并发写入后告警等于最早值（测试 L65-72）；回执后顺延到 audit 期限，不被抹掉（L96-106、L129-143）。
3. **期限不来自调用方**：期限在 runtime 内由 `clock()` 生成（runtime L168），`scheduleAudit` 只做“与账本逐字相等”的核对，不接受调用方改期限（helper L85-88；测试 L92-93）。
4. **严格新预留确认**：仅 `reserved_before_execution`、`execution_attempted===false`、无回执/审计、未冻结、身份一致时才返回 durable ack；已回执/已调度后重复调用被拒（测试 L96-102）。
5. **重启/冻结持久**：冻结后告警清空避免热循环，账本与期限保留；`initialize` 不会重置已有账本（helper L69-74；测试 L120-128）。
6. **自动告警真实触发 runtime 冻结**：receipt 逾期与 audit 逾期两条路径都在真实 alarm 中冻结且 `execution_attempted` 仍为 false（测试 L107-143）。
7. **只接受 SQLite DO 能力**，拒绝 Map/KV（helper L39-41；测试 L37-41）。
8. **fixture 不可部署性（当前）**：fixture 仅被测试和 receipt 引用；仓库内无 wrangler 配置引用它（已 grep）；CI 为 `pull_request`（非 `_target`）、`contents: read`、无 secrets、`--ignore-scripts`。

## 条件（接入生产前必须满足）
- **C1（中）告警被消耗后无人重装**：`service.alarm()`（runtime L249-256）只在发现逾期时写回；若告警触发时时钟读数略早于期限（`<= now` 不成立）、或处理器异常重试耗尽，单个 DO 告警已被消耗，其余未了结期限不再有告警，直到下一次写入。helper 提供了 `reconcileAlarm()`，但 fixture 的 `alarm()` 与文档的构造器示例都没有调用它。要求：DO 的 `alarm()` 在 `service.alarm()` 之后无条件调用 `reconcileAlarm()`，构造器在 `initialize()` 之后也调用一次。
- **C2（中）`reconcileAlarm` 与“已有账本不重装告警”无测试**：`initialize` 对已存在账本只校验、不重装（helper L69-74）；`reconcileAlarm` 没有任何测试覆盖。要求补测：删除告警后 reconcile 能按账本恢复；冻结后为 null。
- **C3（中）缺少端到端用例**：fixture 只用 `policy:{enabled:false}` 建 service，未把 `scheduleAudit` 接入 `createSmallPaymentService`，因此“预留 → 持久确认 → 才允许执行”的顺序（runtime L151-178）没有在 DO 上被真实 `pay()` 走过；重复回执（runtime L192-205 的 `settlement_transaction_already_claimed`）、未知放款结果（L206-216）也只在 runtime 单测层，未在持久化层验证。要求：补一个 `pay()` 经 DO 适配器的离线用例（假 execute/假结算，不涉及真实链），覆盖重复 tx_hash、执行抛错 → `unknown_reconcile_no_retry` → 冻结且告警清空、重启后仍冻结。
- **C4（低-中）解冻后立即重冻的活性问题需明确**：冻结时告警被清空；解冻（新激活）的 `put` 会按账本里仍未了结的逾期条目重装一个“过去”的告警，随后 `alarm()` 立刻再次冻结。这在安全方向上是对的，但 runtime 里**没有任何“对账/补录回执”的入口**（grep 无 reconcile 函数，仅有状态字符串），所以一旦出现 `unknown_reconcile_no_retry`，系统可能永久无法恢复。请在文档中明确这是有意的 fail-closed，或补一条受双签的对账路径（不得自动重试放款）。
