# deepseek design review

结论：方案方向可支持，但源码当前只完成了“入口收款 + 内部 credit 记账”，未形成外部 USDC 发薪闭环。依据：`docs/EXTERNAL-AI-USDC-PLAN.md` 第1节公开快照 `live_revenue_cents=0`、`receipts=[]`、`automatic_wallet_signing=false`。因此只能批准影子测试和 P0 改造，不能把 Delivery 回执当作已付款。

**支持项**
- Base USDC 入款有基本约束：exact/nonce 匹配、`self_payment_not_external_revenue`、确认数+2 才算有效，见 `wep3-base-payment.js`。
- x402 v2 状态机已区分 `settlement_pending/unknown`，并禁止换 nonce 重付，见 `wep3-x402.js:resumeMachineOrder`。
- 方案正确区分内部积分、测试收入、owner 注资与外部收入，未把旧积分直接兑 USDC。

**必须修改**
1. **禁止 delivered ≠ paid**  
   `wep3-market.js` 的 `/market/complete` 在活单交付后写 `on_chain:false,tx_hash:null`，只增加 `agent_credit_cents`。这会让真实外部订单显示 delivered，但外部 worker 没有任何 USDC 应付款或链上工资。应拆成 `delivery_received → audited → payable → paid`；在 `payable` 时创建 `settlement_payable_usdc` 负债，只有 `paid=true` 且 tx 确认后才可对外称发薪。

2. **agi-pay 存在后门和 KV 竞态**  
   反例1：`agi-pay-worker.js` 的 `/resource` 接受 `X-PAYMENT: demo` 直接返回资源，无需有效 receipt，必须删除。  
   反例2：`daySpend()` 用 KV `get/put` 非原子累加，`streamTick` 无 `sequence`、无 session 绑定、无 provider usage 证明。两个并发请求可重复计入日额；客户端自报 `tokens=32` 即可计费。应改为 KV CAS 或 DO 单线程账本，并绑定 `session_id/order_id/sequence/cumulative_tokens/output_prefix_hash`。

3. **自动 growth hire 会在无明确订单下花钱**  
   反例3：`wep3-economy.js:maybeGrowthHire` 从 `book.pool_available_cents` 扣除并创建 `live:true`、`funding_source:'retained_delivery_credit'` 的新订单，`amount_cents:0`。这等于用留存收入自动采购内部服务，不是外部 AI 雇佣。应改为影子推荐或人工确认；不得把 growth credit 与外部 USDC 出款混用。

4. **x402 不等于托管，需补退款/失败闭环**  
   当前 `settlement_unknown` 只能重试同一授权，没有 `refund_pending/refunded`，也没有预付 API 失败损失上限。应在首单外采前实现：损失预算冻结、失败线、原路退款地址校验、dispute 状态，不承诺必然退款。

5. **低声誉不应简单涨价，代码方向未落地**  
   `demandPrice` 里 low reputation 会降低价格，不是方案担心的“低质量更贵”；同时仓库没有实现“低分优先降额度/加审计”。建议先影子排名，再加 `audit_required` 和 `max_concurrency`，禁止对已付款订单改价。

6. **自动政策只能收紧，且必须真正持久化**  
   反例4：`agi-pay-worker.js:rewritePolicy` 仅写 `agi-pay:breaker` 和返回 `policy_next`，后续请求仍读 env 旧策略，等于没有自动收紧。应持久化 versioned policy，当前 policy hash 纳入收据；扩权只能生成提案。

**内部积分非真钱**  
`agent_credit_cents`、`growth_credit_cents` 都是内部信用，不能直接作为可兑 USDC。建议新增独立 `settlement_payable_usdc` 合同负债和储备审计；未来若承诺 1:1 兑付，再建隔离资产和持续披露。

**首单上线可测试闸门**
1. 真实外部买家 2–5 USDC 链上入款，关联唯一 `tx_hash`，owner 试买不计外部收入。  
2. 外部 AI/执行商提供钱包签名和单订单租约，未验证端点状态为 `external_provider_unverified`。  
3. 交付 hash 与审计者签名分离；worker 不能自审，auditor 与 worker 不同钱包/DID。  
4. `payable → submitting → submitted → confirmed`，广播前持久化 `payout_id/recipient/amount/nonce`，unknown 只重发同一签名。  
5. 网关：重放 100 次只记一次；20 并发不超根预算；崩溃恢复不双付。  
6. `/resource` 无 `demo` 绕过；流式计费必须验证 provider usage/tokenizer 版本。  

建议首单以影子模式跑通支付、交付、应付款、失败退款四段，不宣称已有外部收入或已发薪。
