A. Deep 超级代理队列的现状

Deep 超级代理是一个运行在 Cloudflare Worker 上的多席位协作执行体。队列由 GitHub Actions 在 main 收到新的任务卡时触发：桥接脚本把任务 POST 给 Worker，Worker 的持久化任务对象（Durable Object）在 alarm 中依次完成「规划—派发—独立复核—终态记录」。

角色分工必须分清：
- 协调席 deepseek 是规划器（planner），只输出 JSON 计划，不输出 ROUTE 路由行。
- 工作席 doubao、qianwen、kimi、grok 执行具体任务，路由行由工作席产物提供。
- 决策席 gpt 只做最终决策，不参与规划和复核。
- 中转执行席 gpt/claude 只能做有界起草，不能规划、不能复核、不能决策。

B. 代码层面已经定位的原因

1. 协调席被要求「只输出严格 JSON」。一旦它输出散文、解释、路由行或漏字段，整条作业在规划阶段就 blocked，工作席根本没有机会被调用。
2. 规划结果校验是「全有或全无」：一个任务席位非法、重复或任务文本超长，整份计划作废。不会保留合法的任务，也不会给出兜底计划。
3. 派发采用 Promise.allSettled 之后「任一失败即整单失败」的策略。一个工作席 504，会把其他席位已经产出并落盘的真实回答一起丢弃，独立复核也不会运行。
4. 上游超时（HTTP 504）与「原生生成证据不完整」共用同一个错误码 native_generation_evidence_incomplete。复盘时无法区分「模型没答」与「网关超时」。
5. 独立复核席失败时也会整单 blocked，已经产出的工作成果同样被丢弃。
6. 千问席回复「没有可复核项」在旧语义下是正确的：因为整单在复核前就被判失败，确实没有进入复核阶段的产物。

C. 已准备在仓库内实施的修复（等你裁决，不涉及资金、签名或钱包）

1. 规划恢复层：严格校验保留；解析失败时只丢弃非法、重复、超限任务并截断过长任务文本；完全无法解析时，用一个确定性的原生席位兜底，只派一个有界任务，避免同一请求重复派给多个席位造成重复计费。所有恢复都写入 plan_source、plan_issues、coordinator_parse，保留原始输出预览和错误码供审计。
2. 部分成功语义：工作席失败记为 unjudged；只要还有至少一条成功输出，就继续执行独立复核；只有零条输出才整单 blocked。缺失覆盖不会静默放过，终态会升级给决策席，原因写 partial_seat_coverage。
3. 复核不可用语义：独立复核失败时保留工作席输出，把复核标为 unavailable 并升级给决策席，不自动重放同一复核请求。
4. 错误分类：504 记为 upstream_gateway_timeout_504，524 记为 upstream_gateway_timeout_524，请求超时记为 upstream_request_timeout，与 native_generation_evidence_incomplete 分开；中转席同理。
5. 规划提示词补强：明确告诉协调席「你是规划器不是路由器，不要输出 ROUTE 行；每个任务要能在 90 秒窗口内完成，大请求要拆分」。
6. 队列桥接证据白名单同步保留 plan_source、plan_issues、unjudged、coordinator_parse、review.status、review.error，未知字段仍然丢弃。
7. 回归测试：新增协调席散文兜底、非法席位回收、504 部分成功、复核失败保留输出、队列证据白名单等用例；现有部署工作流的完整测试集 158 项全部通过。
