【今天已部署的 B 组：DeepSeek 分层接入与影子路由测量】

背景：DeepSeek 通知 V4.1-Flash 已更新至 1017 版本，并新增网页搜索与抓取 API。本地实测 GET /v1/models 只返回 deepseek-flash 与 deepseek-v4-pro 两个 id，没有单独的 1017 模型 id，所以"换成 1017"在接口层没有可切换对象，1017 是版本说明而不是新模型。这一点先纠正了一个可能的误解。

同时，前一天队列卡在"协调席没吐出路由行"。所以这次不整体换模型，而是分层：主线（plan 席、写卡、分流）继续用 deepseek-v4-pro；Flash 只接新增的只读网页能力，以及作为 worker 路由的候选；路由能力先用影子测试测量，不凭感觉替换。B 组代码提交 d2acd508518b2eb6b13f7947a45d68b8c1d03f50。

B1 只读工具层。新增 scripts/lib/deepseek-tools.mjs 与 CLI scripts/deepseek-tools.mjs，封装官方 Search 与 Fetch。约束：query 最多 128 个 Unicode 字符；count 1 到 50；url 最长 8192 且禁止带 user:password；显式拒绝 localhost、127/8、10/8、192.168/16、172.16-31、169.254、::1、.local、.internal，避免把内网地址送给外部抓取；402 归为 insufficient_balance，408/429/5xx 归为 transient_upstream 且标记 retryable，401/403 归为 auth_or_forbidden；空结果返回 ok 且 charged=false，有结果才 charged=true；所有错误文本脱敏，绝不回显 API Key。测试 scripts/tests/deepseek-tools.test.mjs 共 12 项。

B2 影子测量工具。新增 scripts/deepseek-shadow-routing.mjs，把同一张卡分别发给两个模型，逐行核对输出是否满足"每个 ref 恰好一条 ROUTE 行"。合格判据：0 missing、0 duplicate、0 invalid、0 多余行，且 route_lines 等于 refs_total；加 --require-all-five 时还要求五类 route 都出现。每模型每次只发一次请求，失败只记录不重试。测试 scripts/tests/deepseek-shadow-routing.test.mjs 共 18 项，包含"两个模型都失败时仍然只各调一次"的用例。

B3 实测结果。用的卡是 ops/deep-superagent/tasks/DEEP-SUPERAGENT-20261117-DAILY-1.json，public_distributable，25 个 ref（GROUP A 11 条邮件、GROUP B 6 条仓库观察、GROUP C 8 条邮件）。共 5 次运行、10 次模型调用：

第 1 次，原卡原样、thinking=disabled、max_tokens=2048：pro 与 flash 都返回 planner JSON，ROUTE 行 0 条，pro 有 21 行非 ROUTE。回执 shadow-20261118T022602Z.json。
第 2 次，worker 口径、thinking=disabled、2048：pro 8/19，flash 覆盖 19/19 但 9 行被判 unknown_ref。回执 shadow-20261118T022700Z.json。
第 3 次，worker 口径、thinking=disabled、2048：pro 8/25（只答 C 组），flash 25/25 且 pass=true。回执 shadow-20261118T022740Z.json。
第 4 次，worker 口径、thinking=enabled、4096：两模型 finish_reason=length，输出 0 字符。回执 shadow-20261118T022802Z.json。
第 5 次，worker 口径、thinking=enabled、8192：两模型同样 length 且 0 字符。回执 shadow-20261118T022922Z.json。

第 2 次的 9 行 unknown_ref 是测量端缺陷，不是模型错误：卡里 GROUP B 写作 B1 到 B6，不是 16 位哈希，第一版 ref 提取只认哈希。已修并补测试，第 3 次才是有效对照。这一点我主动写出来，是因为不希望在证据里留下一个会被误读为"Flash 乱输出"的数字。

B4 四个发现。

F1 卡本身混了两套契约。同一张卡里既有"Planner deepseek: return ONLY JSON"，又有"Worker: return ONLY one line per ref"。两个模型都选择先满足 planner 契约，于是 ROUTE 行 0 条。这与"协调席没吐出路由行"是同一个失败面：不是模型不会分诊，而是指令在互相抵消。

F2 在 worker 口径下 Flash 没有更差，反而更全。同一提示词，Flash 25/25 全覆盖、无多余行、无 markdown；Pro 只覆盖 8/25 并停在 C 组。此前"Flash 一次给齐多组路由行大概率更差"的猜测，在这张卡上不成立。

F3 thinking 开启会把完成预算烧光。thinking=enabled 时，4096 与 8192 两种预算下两模型都是 finish_reason=length、输出 0 字符。而 scripts/call-deepseek.mjs 的默认正是 thinking='enabled'、maxTokens=8192。任何沿用默认值调用长卡的既有入口，都有拿到空正文的风险。这是我今天认为最值得优先修的一条，因为它能解释"协调席没吐出路由行"而完全不涉及模型能力差异。

F4 单样本。只测了一张卡、每模型各一次。Pro 的 8/25 也可能来自卡里"WORKER COVERAGE 写了三个席位"导致的自限，需要在拆卡后复测才能定性。

B5 配置与工作流。config/ai-providers.json 的 providers.deepseek 下新增 tiers：main_line（deepseek-v4-pro，planner/写卡/分流，thinking enabled）、worker_routing（thinking disabled，min_max_tokens 4096）、web_tools（只读 Search/Fetch，无模型调用，按成功请求计费 5 元/1000 次）。default_model 没有改。新增 .github/workflows/deepseek-shadow-routing.yml，只有 workflow_dispatch，没有 cron，只上传 artifact，不写仓库、不部署。已确认该工作流被 GitHub 正确注册为 active，说明 YAML 可解析。

B6 成本与未做。10 次调用合计约 4.8 万 tokens，未与账单核对，api_bill_verified=false。没有把 Flash 写进路由链路；没有把 search/fetch 接进 SOURCE-INTEL 抓取步骤（目前只有模块与 CLI）；没有定时调用；没有改生产 dispatcher；没有生产部署；没有资金动作。
