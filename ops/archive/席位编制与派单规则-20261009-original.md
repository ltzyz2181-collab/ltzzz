## 三、WorkBuddy 的"常驻扫描 Hub"——**明说：目前未验证**

owner 两次点到这件事，**必须如实回答**：

| 项 | 事实 |
|---|---|
| 是否已有常驻扫描？ | ❌ **未验证 / 未上线** |
| 已做什么？ | 写好 `dispatch-sentinel.yml` + `scripts/dispatch-sentinel.mjs`（每小时扫描），**本次已推入仓库**；跑没跑起来，以 `memory/sentinel/` 是否出现落盘为准 |
| 明确结论 | **在仓库出现连续 ≥3 小时的 `memory/sentinel/` 落盘之前，"常驻扫描"一律记为未验证。** |

**"未验证"的三个具体含义**（供其他 AI 对齐）：
1. **未跑过一次真实调度** —— 没有 `memory/sentinel/*.md` 的产出证据
2. **无运行日志可查** —— 我读不到 Actions run 日志（能力边界）
3. **落盘即证据** —— 工作流跑成会自动 commit `memory/sentinel/YYYY-MM-DD-HH.md`，这是唯一可核验凭证

→ **判定标准（可自查）**：`memory/sentinel/` 下出现连续 ≥3 个不同小时的落盘文件 = 已验证；否则 = 未验证。

## 四、没有 key 怎么给 WorkBuddy 派单？（owner 亲自问的核心问题）

owner 问：「你的任务怎么执行？没有你的 key 怎么给你派单？你有什么解决方式？」

### 4.1 先说清 WorkBuddy 的"key 现状"

| 项 | 事实 |
|---|---|
| WorkBuddy **需要 AI 模型 key 吗？** | **不需要** —— 它是执行体，不是被调用的 API |
| 它**有什么凭据？** | GitHub 写通道、Cloudflare Token |
| 它**缺什么？** | ❌ 无 git 凭据、❌ 无 Actions 手动触发权、❌ 无常驻进程 |

**关键结论：给 WorkBuddy 派单，从来不需要"给它的 key"——需要的是"它能读到的任务文件"。**

### 4.2 四种可行的派单方式（按可靠度排序）

| 方式 | 怎么做 | 需要 key？ | 可靠度 |
|---|---|---|---|
| **① Hub 文件派单（推荐）** | owner/总控把任务写入 `ops/dispatch/*.md`（或 `memory/daily/`）；WorkBuddy 读文件即接单 | ❌ | 🟢 最高 |
| **② 接单回执制** | 读派单 → 写 `ops/接单回执-*.md`（含单号/职责/边界）→ 查仓库即知收到 | ❌ | 🟢 高 |
| **③ Actions 定时触发** | 任务做成工作流，**它自己跑**，不需要人醒着 | ❌ | 🟢 高 |
| **④ 对话直接下派** | owner 在对话里直接说 | ❌ | 🟡 中（依赖会话存在）|

**核心洞察**：**"派单"的本质是"任务落盘到执行体能读的地方"，不是"给一把 key"。**
