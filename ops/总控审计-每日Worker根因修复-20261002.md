## 一、根因：所有 AI 每天在"盲写"（最严重）

`scanRepo()` 声称"每天先通读仓库"，实际：
- **v2**：只用 `resp.ok` 判"可读"，从不读正文 → AI 收到的记忆是空清单。
- 实测铁证：DeepSeek 09-30/10-02 产出原话——"我没有实际访问你本地仓库的能力""仓库里我暂时没有找到装备论的原始文本"。它诚实地说自己没读到，但 Worker 仍把产出标记 `dry_run:false`（成功）。
- 更糟：`renderScanSection` 把 manifest 对象数组直接 `${f}` 渲染成 **`[object Object]`**，文件清单全是乱码。

**修复 v5（根因级）**：Worker 改为**直连 GitHub raw 并行拉取正文**（Promise.all + 单文件 8s 超时），注入 prompt（上限 24KB），彻底去掉不稳定的中间网关层（daily→gateway→raw 两跳在免费额度下 0/10）。
**验证**：修复后 deepseek-daily 实测 `GitHub raw 并行直读：10/10 文件可读，注入正文 14596 字节`；产出含真实记忆特征词（承负×5、太乙金华×2、识神一点触动×2、NPC×4）；DeepSeek 不再说"读不到"，改为产出实质的"传统文化×装备论"对照表。

## 五、微信菜单"点了没反应"诊断

- `ltzzz-wechat-publisher` Worker **已部署、凭证齐全**（health: app_id:true, has_secret:true, r2:true, auto_mass:false）。
- 但它只有 `/health` 和 `/publish` 两个端点，**没有消息/事件回调端点**（`/wechat`、`/callback`、`/menu` 全 404）。
- 判定：菜单若为 **view 型（跳转网页）** → 点它直接开 ltzzz.com，本就该能用，无需改代码；若为 **click 型（推事件/发消息）** → 微信把点击事件 POST 到"服务器配置"里的回调 URL，而 Worker 未实现该回调 → 收不到、不回话。
- **需 owner 确认**：① 菜单项是哪种类型（view 还是 click）；② 若是 click，需在 mp.weixin.qq.com「服务器配置」填 URL+Token 并启用，Token 要与 Worker 签名校验用的一致——这一步只能 owner 在微信后台做，AI 不代登。
- 确认类型后，若需 click 回调，总控再实现 `/wechat` 端点（GET 验签 echostr + POST 收 XML 回消息）并部署。
