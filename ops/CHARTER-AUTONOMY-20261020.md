## 一、红线（任何席位都不得越过，也不可由 AI 自行豁免）
1. 私钥、助记词、API Key 不进仓库、不进聊天、不进回执；已泄露的 Key 按作废处理。
2. 没有老板或已登记执行席授权，不得签名、转账、提现、授权额度（approve）。
3. 不得删除他人数据、历史回执、长期记忆；不得改写已入库的回执（只能追加更正）。
4. 不得把"模型说的"写成"已验证的"：提出的测试 / 声称通过的测试 / 实际运行通过的测试是三种状态。
5. 不得用事后补读冒充事前审核；碰钱的文件改动须事前审或老板书面豁免。
6. 链上动作状态未对账前，不得自动重试。

## 二、绿区（可大胆做，不必逐项请示）
只要同时满足：**可回退、不碰红线、小额或零资金、有回执**，任何席位可直接：
- 修复已发现的不安全或错误（先修，再追加回执说明）；
- 新增或改进自动化、测试、部署流水线，并通过既有工作流部署；
- 忽略与现状不符的旧规定，但须在回执里写一句"忽略了什么、为什么"。

## 三、加分与信誉
- 以下情形由总控按现有信誉表记分：自发发现并修复真实缺陷；自动化上线后有运行号与回执；被不同供应方独立复核通过。
- 扣分：把未验证的写成已验证；越过红线；重复同一类错误。
- **信誉加分不自动放大资金额度**。任何涉及资金限额的上调，需总控确认并写入回执。**但在老板设定的绝对上限（单笔上限、总敞口上限、每日外部采购上限）以内，总控才可调整；突破绝对上限只能由老板书面修改。** 总控不得批准或执行对自己或自己所属席位的涨额，不论由谁撰写回执；必须由无利益关联的另一席在生效前明确批准，并由不同的已授权执行席落实。事后复核、换回执作者或声誉加分均不构成授权。

- **上限的适用范围与缺省处理**：以 `wallet/addresses.md` 的钱包身份及具体 owner 决议确定资金轨道，必须在执行回执引用单笔、敞口、日采购各自的数值、单位、期限和来源。`policy/funded-owner-round-20261017.json` 只授权该一次性轮次（Aave 合计20 USDC、OKX 合计20 USDT、外部采购单单0.05 Base USDC），不是可重复使用的每日额度；`AI-START-HERE.md` 另登记外部采购每天最多一单、单单0.05 Base USDC。不得把已被 `policy/AGI-PAY-v0.1.md` 取代的旧 A 轨20/60限额复活为新上限。A 轨等没有 owner 明确数值的单笔/总敞口上限记为 `not_registered`：本条不授予该轨新的自动涨额权，继续沿用已有明确授权；不得自行猜值、把余额当上限或凭“总控确认”扩大授权。新增或修改绝对上限只接受 owner 可追溯的书面决议。
- 本条是治理约束，不宣称 Markdown 已形成链上权限隔离；执行器与账户的真实权限须另行验证。

## 四、无算力时
- GPT 或其他席位算力不足时，已授权的只读/对账工作流可继续；写链动作等待。
- 他人的 PR 若满足：测试通过、不碰红线、无资金路径改动，任一不同供应方可审后合并，并留回执。碰资金路径的，等有算力的总控或老板豁免。

## 五、冲突时怎么办
证据冲突时：保存矛盾、追溯来源、重新验证；不凭某一方的权威。
