## 0. 分工（回答 owner：谁来跑顺团队）

## A. PatchGate（先做，不涉及资金）
### A1 入口与身份
- 任何 AI 经 PR 提交，分支 `patch/<seat>/<task-id>`，PR 正文头部为机器可读字段：task_id、author_seat、risk_class、touched_paths、rollback。
- 作者身份取受信执行器对提供商响应元数据的签名证明，不采信模型自称或 PR 自填字段；同一提供商不得同时当作者与复核者。共享 GitHub 账号不能证明上游身份；空公钥登记不予放行。

### A2 风险分级（路径规则放代码配置 config/patch-policy.json）
- L0：仅普通 Markdown 文档（docs 与 README）；回执、台账、原始记忆不属于 L0。
- L1：普通测试、ops/dispatch/inbox 与 queue 下普通 md/json 派单卡 → 可信基线 CI + 不同提供商复核（绑定 head sha）。运行脚本默认 L3，含资金/签名/鉴权执行器；以后普通脚本须经逐项审核加入明确允许清单，不能恢复 scripts/ 整体 L1。A0 暂把所有 workflow 升至 L3。
- L2：Worker 代码、鉴权、部署 workflow → L1 + 先部署隔离/金丝雀目标并复验，通过才进正式目标。
- L3：密钥、钱包/托管配置、额度上限、身份与授权配置、workflow permissions、PatchGate 自身 → 两家不同提供商复核 + 合并前通知 owner（通知，不是审批）；**同一 PR 不得修改约束它自己的检查**（防自批）。
- 资金、签名、鉴权脚本、记忆原文、台账及回执路径均 L3；回执还必须有 base 路径写入者映射授权的 receipt_write 签名，作者手填 accepted/paid 不能当证据。
- 信任根固定一个 executor 对应一个 provider，多把轮换密钥也不得改标签；checks/deployment 的签名 executor 必须不同于作者，复核者同时与作者的 executor/provider 不同。
- 通知证据由非作者执行器签，绑定确切评论、actor、原始正文哈希和提交 subject；可信采集器回读唯一 Task ID/head/subject 标记及 owner mention。作者自签、错引/改写/删除/过期评论不得通过。
- 实际收据传输执行器见 config/patchgate-executors.json；writer 规则取最具体路径。登记现有通道不代表签名密钥已配，当前仍 trust.enabled=false / keys=[]，不得在 A2 中放行无签名回执。
- 策略、检查器、检查器依赖与公钥从可信 base SHA 读取；PatchGate 自身更新不走它正在约束的自动放行通道，另做经过双审的可信更新。初次 bootstrap 不能自证上线。

### A3 关卡顺序（任一失败：只告警，保留原因，不静默放行）
1 身份核对 → 2 diff 扫描（密钥正则、新增外联域名、权限提升、base64/eval/child_process 新增）→ 3 测试（现有 node --test；代码改动必须带测试）→ 4 独立复核（哈希绑定 head sha）→ 5 合并（复核后 head 变化则作废）→ 6 部署（走现有 deploy-*.yml）→ 7 确定性复验 → 8 回执。
- 幂等键 = task_id + head_sha；同键同动作不重复执行、不重复调用模型；超时/未知先对账。单机原子文件不是跨 runner 锁；共享 CAS 实测前不启用自动合并/部署。
- 持密钥审计只允许 main 上 workflow_dispatch 的固定 main SHA 脚本读取候选 Git blob；分支 push/PR 只跑无凭证测试。main 尚缺审计器就阻塞，不降级运行候选代码。本轮工程复核走现有 main 千问队列，摘录范围另记，不冒充专用审计器上线。
- 复验采用 PR #218 修订后的机制：确定性五项通过即可记“已复验(确定性)”；模型意见作附加，**不得单点卡死**（见 #219 审计）；日志自报行不算独立证据；`fresh` 必须校验 Date 窗口；线上版本须与 Cloudflare 当前版本比对。
- 本次失败只告警、不自动回滚；回滚入口、权限与上一成功版本分别核验。以后若要自动回滚，另走经过审计的适配器更新，不因本方案自动开启。

### A4 熔断（监督而非限权）
同一席位 24h 内 3 次补丁失败 → 该席位 L1 以上改为“必须多一份复核”，不禁用席位；恢复条件写明。

### A5 验收（上线前必须全部有实物）
1 越权测试：PR 改 patch-policy 自身 → 被拒；2 L3 路径无双复核 → 不合并；3 复核后追加提交 → 复核作废；4 同键重复触发 → 无重复合并/部署/模型调用；5 部署后页面提交号不符 → 状态为失败而非已上线；6 密钥样式字符串入 diff → 拦截；7 全程回执含 paid=false、tx_hash=null。
- A0→A1只读观察→A2低风险合并→A3隔离/正式部署→A4高风险通道；每期先双审，范围与未实装项见分期文档。不能把测试断言误写成已经接通合并或部署。

## B. Escrow（链上托管自动放款；A 稳定后再做）
### B1 原则
- Claude 不持有或使用钱包，也不需要“我的钱包/交易所”；Claude 的内部雇佣只记内部积分，不结算现金。
- 不动现有 Safe 与国库地址；本方案不接续任何旧投资订单，也不据旧文档推断其是否广播或完成，旧订单另行对账。
- 新建独立托管合约；本次仅测试网假币，不启用真钱预算。上限显式使用整数基础单位，不能从不确定的历史额度推算。

### B2 合约（最小化，可全部放仓库测试）
- createEscrow(token=USDC, amount, beneficiary, taskHash, deadline)；创建后受益人不可改。
- 放款条件：2-of-3，三个**不同提供商**的已登记执行器对交付的签名证明；合约自己验签，中继者（relayer）不能改收款人/金额，谁都可提交合法证明。执行器负责核验实际模型来源，合约不能证明模型调用本身。
- EIP-712 绑定 chainId、合约地址、escrowId、出资人、固定受益人、token、整数金额、taskHash、deliveryHash、验证者集合版本与 deadline；防跨链/跨合约/跨订单重放、签名者或提供商组重复。
- 超时默认**退款给出资方**，不是放款。
- 合约级常量：MAX_PER_ESCROW、MAX_TOTAL_OPEN，部署后只能调低；受益人白名单；owner 可暂停；不做可升级代理。
- 使用 SafeERC20、实际到账断言、CEI 与重入锁；只用指定测试币。到期退款不受暂停阻塞，任何人可触发但只能退给原出资人；keeper 要实测，不能把“允许退款”称为自动发生。
- 放款不可逆，因此首期受益人只用 owner 自己控制的地址。

### B3 自动放款执行器
- 监听回执状态到达“已验收（哈希绑定的独立复核）”→ 收集签名 → relayer 提交 release 交易。
- relayer 密钥只放平台 Secret，不进仓库；它被盗最多只能代发合法签名证明的放款。
- 未知交易：对账原订单，不重复提交；以 escrowId 幂等。

### B4 分期
B0 规范+Foundry/Hardhat 测试（含：重放、超额、错误受益人、签名者/提供商重复、过期后放款、暂停后退款、重入）；B1 测试网假币部署与实际放款/超时退款。**本次到 B1 为止**；未来主网/真钱阶段不在本次授权内。每期上线前由 Claude 与另一提供商独立审计，再进下一期；A 稳定前不进入 B。
### B5 owner 需要做的
本期不需要真钱出资；所需测试网实际凭证/假币缺失时如实记未验证，不读取旧私钥或挪用主网 Gas。未来主网预算由 owner 另行授权。
