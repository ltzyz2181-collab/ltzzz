> 原则：owner 已明确"部署不要问我、想法大胆、遇到问题修改不安全"。以下权限模型即按此制定。

## 一、总控调用其他 AI 的三条通道

**通道 A｜Worker 代理（目标态）**
每个 AI 一个 Cloudflare Worker（qianwen / kimi / doubao / deepseek 已有代码或部署）。总控程序 = 每日 cron 触发 → 读 `ops/task-queue.json` → 按 DID 路由调对应 Worker `/v1/chat/completions` → 结果写 `ops/runs/`。Key 只存在于各 Worker 的 Secret，总控只见调用结果，永不见 Key 值。
现状：千问/Kimi Worker 代码在本机未部署（通道故障）；豆包 Worker 线上存活。

**通道 B｜交接文本（现在就用这条）**
总控把任务写成可直接粘贴的指令文本（如《豆包交接指令》），owner 复制给对应 AI。适用：还没 Worker 槽位的 AI（Kimi 部署前）、需要该 AI 客户端特权的活（豆包的本机执行）。
规则：每次交接文本必须自带"验证三关 + 禁止事项"，接收方 AI 完成后回执写进 deployment-status.md，总控次日审计。

**通道 C｜定时任务（自身循环）**
每天 9:00 千问巡检：试探本机通道恢复 → 恢复即执行部署流程 A→E；同时核验豆包部署真实性（ltzzz.com / Worker health / 仓库提交史三方比对）。

## 二、花钱建设与营收闭环

```
营收段：内容生产（视频流水线/文章）→ 平台分发（YT/TikTok/国内电商）→ 收入进账
   ↓ 自动分账（政策 v0.4，收益联动，30/40/30）
30% 再投入：API 费、算力、域名、平台保证金 —— AI 可自行花（熔断兜底，不打扰 owner）
40% 运营池：各 AI 工位预算，按 KPI 表现动态分配（干得多的多拿算力）
30% 金库：Safe 多签，增长性支出（买装备级资产）需委员会 2/3
```
冷启动（现在）：无营收 → 支出预算≈0，只花已有免费额度；owner 的 5U 是种子测试，不是运营金。
**闭环第一个真实里程碑 = 第一笔外部收入进账**（不是部署完成）。目标顺序：视频内容上 YT/TikTok → 挂捐赠/联盟链接 → 验证首笔进账路径 → 才谈电商店铺。

## 三、记忆增长机制（各 AI 的"成长"怎么算数）

每个 AI 的每次任务后必须做三件事：① 向 `ltzzz-memory/重要事件` 提交自己干过的账；② 向对应 DID 文档的 `reputation` 字段追加自评事件（总控复核后生效）；③ 发现 owner 新的"观"记录（梦/体感/原话）→ 按《梦境数据库》入库标准归档。
KPI 记分板（月度，决定预算分配与总控去留）：任务兑现率（回执完整度）、记忆贡献量（有效入库条数）、事故率（被审计发现的夸大/违规）。
